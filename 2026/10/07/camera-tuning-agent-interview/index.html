适用岗位：大模型应用开发、Agent 应用开发、LLM 工程师。

本手册按能力主题重组，标明准备优先级、理解难度和答题抓手，共 79 道项目与工程问答 + 8 道性能评测专项问答，共 87 题 。覆盖需求理解、RAG/GraphRAG、Agent、HIL、Python 服务开发、异步任务、数据权限、模型接入、部署评测、Harness Engineering、Hermes Agent，以及运行时内存与记忆管理。尚未提供具体招聘 JD，岗位覆盖按常见 AI 应用开发职责整理；这代表学习范围，不表示项目已经使用文中全部技术。

本文以已确认的链路为主线：用户需求与意图识别 → 首次 QCAT 评测建立基线 → 模型结合需求与指标从 GraphRAG 召回参数定义、人工成功方案和调参知识 → 模型推荐方案 → 结合已有方案与搜索生成候选批次 → 每次实验调用执行一个候选 → 整批结果反馈给模型 → 判断停止或进入下一轮，自动调参成功后将结果持久化到数据库。 当前有依据的表述是“模型辅助决策、已有方案复用与候选搜索、按批次反馈的 ReAct 式闭环”。候选 JSON 与独立的高层步骤计划需要分别核实，不能仅因文件名含 plan 就认定有高层 Plan-and-Execute。

数据库中的知识包括参数定义与已有方案，检索会召回之前人工调参的成功方案。GraphRAG 组织参数描述和参数之间的影响关系，并做了社区发现；当前参数选择与调整建议主要依赖大模型推理。知识材料可能采用 Markdown、HTML、PDF 等形式；实际解析器、切分和 embedding 配置仍需核对。社区信息如何进入提示词、候选值生成规则，以及成功结果入库后何时更新检索索引，也需结合实际代码补齐。下文另列“图谱提供证据、模型提出方案、程序约束搜索、QCAT 验证结果”的改进设计，不把建议写成已经落地的能力。

零、现有执行流程与完整项目口述

面试官问：从用户提出需求到下一轮调参，实际怎么执行？

可直接口述的回答：

系统先理解用户的需求场景、目标和约束，运行一次 QCAT 评测建立初始基线。模型结合需求与初始指标，从 GraphRAG 召回参数定义、描述、之前人工调参的成功方案和参数影响关系，再提出本轮调整建议。图谱已经做了社区发现，目前参数选择与方案建议主要依赖大模型推理。

候选来源包括召回的已有成功方案，以及围绕相关参数进行搜索得到的配置。笛卡尔积是候选展开方式之一，不能概括整个系统；是否直接采用原方案、以其为起点局部调整，以及两类候选的顺序和比例，按实际策略说明。候选组织成一批实验配置。已有执行流程负责把参数配置落实为实验输入；硬件侧的机械臂、光源箱和手机操作已经有固定方法，一次实验接口调用完成一个候选配置的整套实验，上层不需要让模型逐个指挥底层设备动作。

整批候选完成评测后，系统汇总各候选的图像和指标，再由模型统一分析并推荐下一批调整。不是每完成一个候选就调用一次模型。达到目标、达到最大迭代轮数或连续无改善时结束，其中轮数上限可配置。自动调参成功后，结果会持续持久化到数据库。最终应分别报告执行状态、目标达成情况和停止原因；入库不等于图谱、向量索引和社区信息已经同步更新。

因此，可以描述为“模型辅助决策、已有方案复用与候选搜索、工具执行实验、按批次反馈的 ReAct 式闭环”。候选 JSON 是批次级实验计划及结果载体，独立的高层步骤规划需要另外提供实现证据。

候选、批次和决策轮次如何区分？

单位 含义 不能混淆的地方
一个候选配置 一组具体实验参数及其产物 对应一次完整实验调用
一个候选批次 本轮需要执行的多个候选 可有多次实验调用；是否并行由调度实现决定
一轮决策与实验反馈 本轮建议、候选批次、整批执行和汇总反馈 30 个候选不等于 30 轮模型决策
最大迭代轮数 允许继续探索的批次数上限，可配置 只限制轮数不能单独限制总实验量

初始基线建议单独记录，计入总耗时和总资源成本；是否占用迭代轮次要在接口约定中写清楚，不能把这里的建议当成当前计数代码。

plan30_sim.json 的实际结构是什么？

该样例有 type、simulation、qcat_fail_info、plan 和 raw 五个顶层字段。plan 有 30 个候选，每个候选包含 plan_id、tuning_bin_path、image 和 IQ_info；IQ_info 再区分 score 与 result。

样例已经带有图像及评测结果，因此是包含执行后反馈的记录。它的 simulation 为字符串 "True"，不能把这份仿真样例等同于实机执行轨迹；接口接入时应显式处理字符串布尔值，不能直接使用 bool("False")。参数和数字编码在 plan_id 中，没有独立结构化参数对象，值的语义及生成过程仍需核对。

本节均为建议设计，不表示当前已经实现。 当前事实是 GraphRAG 有影响关系和社区发现，检索包含人工成功方案，自动成功结果会入库；方案推荐依赖模型推理，笛卡尔积只是候选搜索的一部分；改进目标是在保留模型决策能力的同时，使参数依据、实验规模和验收行为可检查。

环节 建议处理 解决的问题
1. 定义任务 记录主要优化指标、保护指标、平台/场景/配置版本和初始基线 避免只提高某项评分却破坏用户约束
2. 图谱取证 同时召回已有成功方案与参数定义，核对适用条件，再查询影响关系、所属社区和重要跨社区关系 给联合调整提供依据，避免遗漏耦合参数

7. 下一轮决策 给模型基线、有效候选摘要、失败原因、指标变化和剩余预算 用外部反馈决定范围细化、加入耦合参数或换方向

结构化搜索计划建议字段（不是现有 JSON schema）：

这份建议计划可由适配层展开成现有 plan[] 候选输入；不要直接替换既有实验接口 schema。模型输出可以先做一次受预算约束的修正，仍无法满足参数或预算规则时返回明确原因，不能静默截断组合或忽略保护指标。

先检查方案适用性，再决定探索范围。 建议对历史成功方案检查平台、场景、配置版本与目标约束，可用时先验证完整配置；不完全匹配时由模型提出需要修改的部分。这个优先验证策略是改进建议，不代表当前已按此排序。不要把一个完整成功方案拆成参数值后与其他方案任意交叉，原有联合配置的有效性可能因此丢失。成功持久化已经存在，改进重点是方案溯源、发布版本与后续复用的可验证性。

笛卡尔积预算与分组策略。 以下乘积只计算需要展开的搜索分支，整个批次还应计入历史方案验证候选；合并去重后计算真实实验数，有意复测单独计费。若第 i 个参数有 k_i 个值，组合数量为所有 k_i 的乘积；例如 8 个参数各取 3 个值，会有 6,561 个候选。生成前先计算数量，检查已定义约束，并在实验提交前核对实际候选量。超过预算时明确缩小范围、减少候选值、按关联参数分组或采用抽样，不把抽样结果称为完整笛卡尔积。

可以先选择与当前目标直接相关的小参数组，用较少的离散值粗搜索，再根据整批结果细化较好区域。社区结构为分组提供线索，显式影响关系与适用条件仍需核对；一个社区不一定全部参与搜索，不同社区也不保证独立。分组与粗到细会牺牲一部分全局搜索覆盖，应保留重要跨组关系并做最终联合验证。预算仍不足时再比较抽样或其他搜索方法，不把引入复杂优化器当成默认要求。

最佳候选与停止规则。 建议由程序按预先定义的规则判定：先识别实验有效性，再检查硬约束与目标，最后按业务认可的排序规则比较。失败或结果缺失的实验单列；达标候选中可以比较主要收益、稳定性和成本；未达标候选可以保留为“当前最佳未达标”，但不能覆盖已有达标候选而不检查约束。若所有候选都未达标，应预先定义约束违反程度与主要收益之间的选择规则，避免模型临时偏向某一项分数。候选落在不同权衡方向时可保留多个备选，并由业务规则或必要的人评决策。

连续无改善建议按完整批次统计：比较有效候选与历史最佳是否有超过最小有效幅度的进步，连续窗口与幅度都可配置，幅度参考同一配置重复测量的波动校准。整批工具失败属于执行异常，不能直接当作搜索无进展；保护指标回退也不能仅凭综合分上升视作改善。达标、预算耗尽和无改善应有不同停止原因。当前具体评分函数、窗口和幅度尚未确认，这些属于待实现或待核对规则。

对照 改变什么 重点观察
A：当前方案召回、模型推理与候选搜索 作为现有基线 目标达成率、无效实验、耗时和保护指标退化

Q02：为什么需要模型做意图识别？关键词匹配不能做吗？

参考答案：

用户通常描述的是场景和感受，比如“夜景颗粒明显，但不要把细节抹掉”，不一定知道对应的参数名。模型的作用是理解语义、提取目标和约束，把不同说法转换成适合检索的需求表达。

对于固定术语或明确参数名，关键词和精确匹配很有效，可以作为基线或补充。模型是否有价值，要看它在口语表达、多目标和省略信息上的识别效果。后续算法解决的是给定参数后的执行或优化问题，模型与 RAG 负责前面的“需求对应哪些参数”。

回答重点： 能否把自然语言需求准确映射到知识库中的相关参数，是最直接的价值验证。

Q03：意图识别输出什么？如何处理模糊需求？

备考定位：A · 核心必答｜基础。 答题抓手：结构化意图、多目标约束与缺失条件。

参考答案：

意图识别应输出适合检索和后续接口使用的结构化信息。可以包括场景、用户观察到的问题、目标、约束、已知平台条件，以及缺失但必要的信息。具体字段要与实际实现一致。

例如“夜景降噪但保留细节”同时包含场景、改善目标和保留约束，不能只识别出“降噪”两个字。对于“画质不太好”这样的宽泛输入，应请求补充会影响召回的关键条件，或先返回候选问题类别。不能自行补出用户没有提供的硬件版本、数值目标或问题根因。

回答重点： 保留多目标及其关系；关键缺失信息单独记录。模型自报置信度不一定校准，应结合标注集、字段完整性和召回结果验证，而不是直接把它当概率。

参考答案：约 90 秒完整版本

用户需求先被整理成场景、目标和约束，初始 QCAT 评测给出当前配置的基线。模型查询 GraphRAG 中的参数描述、方案和影响关系，并结合评测结果推荐调整。候选可以来自已有人工成功方案，也可以来自笛卡尔积等参数搜索；各参数候选值的具体生成规则，需要按真实代码进一步说明。

执行侧的实验工具一次完成一个候选，内部用固定方法协调设备；模型不需要逐个决定机械臂、光源箱和手机动作。整个候选批次完成后，系统汇总指标和图像，模型再分析并提出下一批建议。一次候选实验、一个候选批次和一次模型决策轮次是不同单位。

这个过程体现“观测—推荐—执行—新观测”的反馈决策，但不一定采用标准的原生 tool-calling 消息格式，所以我会用 ReAct 式闭环表述。若面试官问独立的 Planner / Executor 或高层 P-E，我会展示实际步骤计划及消费逻辑；仅有 plan[] 列表时，不声称已经具备高层规划或自动重规划。

Q05：为什么选 LangGraph，而不是普通 Python 循环？

备考定位：A · 核心必答｜进阶。 答题抓手：状态图的选型依据，以及相对普通循环的代价。

参考答案：

普通代码也能实现这条主线。LangGraph 可以把意图识别、初始评测、参数检索、模型推荐、批次生成、实验调度、结果汇总与停止判断表达为明确节点。当前节点划分需按实际图说明；HIL、校验修正和恢复是可增加的设计。已有单候选实验接口可以被图节点调用，不需要把每个底层设备动作拆成 Agent 节点。

框架也有成本，例如状态合并规则、checkpoint 配置、调试和版本依赖。如果流程只是固定的一次模型调用加一次工具调用，引入图框架的收益可能不大。我的选型依据应是实际存在的分支和生命周期复杂度。

常见追问： 用了 LangGraph 就自动支持持久化恢复了吗？

回答重点： 没有。需要配置持久化机制、线程/任务标识和恢复流程；外部工具副作用仍需要单独处理。

Q06：State 怎么设计？为什么不只用 messages？

备考定位：A · 核心必答｜难点。 答题抓手：业务状态、消息、计划版本与外部任务引用。

参考答案：

messages 适合保存模型交互，但主线还需要结构化字段。建议区分用户需求、结构化意图、初始基线、召回参数与关系来源、本轮建议、批次 ID、候选状态、历史最佳、剩余预算和停止原因。计划与运行状态分开维护，才能说明恢复的是哪一轮批次、哪些候选已完成。候选完成数量不能直接作为模型迭代轮数。

意图、检索结果和实际提交的参数集合应分开保存，才能追踪信息在哪一步发生变化。后续流程已有自己的实验历史和最佳方案时，前端 State 可以只保存关联 ID，避免重复维护两份事实。图像和完整日志存外部存储，State 保存引用。

常见追问： 并行更新字段怎么办？

回答重点： 明确覆盖字段与聚合字段，为聚合字段设计 reducer；多路检索可分别保存结果，再按参数身份去重、合并来源，不能简单覆盖其他分支的召回结果。

Q07：这是单 Agent 还是多 Agent？需要拆多个 Agent 吗？

备考定位：C · 按岗扩展｜基础。 答题抓手：独立决策主体与多个工作流节点的区别。

参考答案：

多个节点或多个工具不等于多个 Agent。意图识别节点、RAG 节点和现有流程入口本身不能证明是多 Agent；若没有多个独立决策主体，描述为一个模型应用工作流即可。

只有在独立任务可以并行、上下文需要隔离或不同职责确实有独立决策需求时，我才会考虑多 Agent。拆分后需要评估协调成本、重复调用和错误传播，不能仅因为有“规划、执行、评估”三个名字就认为必须用三个 Agent。

常见追问： 独立评估 Agent 能保证结果正确吗？

回答重点： 不能。模型评审可以辅助，但客观约束和工具执行结果仍要独立验证。

Q40：多轮对话中，用户纠正了场景，你怎么更新意图？

备考定位：B · 重点追问｜进阶。 答题抓手：用户纠正后的状态更新与旧约束失效。

参考答案：

把新增信息、纠正信息和新任务分开处理。例如用户说“不是夜景，是室内逆光”，应替换场景字段，同时保留仍然有效的“保留细节”等约束。保存原始消息和结构化意图版本，必要时确认含义，而不是把所有历史条件简单累加。

如果场景变化影响参数适用性，需要重新检索并生成新的请求版本。旧计划的审核结果不能自动授权新计划。任务已经在设备执行时，还要区分变更请求和当前执行实例，根据是否支持取消选择等待、取消或创建后续任务。

常见追问： 长期记忆中的用户偏好和本次明确要求冲突怎么办？

回答： 本次明确要求优先；长期偏好只补充未指定信息，并保留来源与可撤销性，不能覆盖当前任务约束。

Q41：用户说的是现象，你为什么认为已经知道根因？

备考定位：B · 重点追问｜进阶。 答题抓手：区分现象、根因假设与已验证结论。

参考答案：

意图识别首先提取用户观察和希望改善的目标。比如“照片模糊”不能直接等价为“锐化不足”；根因应作为待验证假设，信息不足时澄清必要条件或检索多个候选方向。

查询改写要保留原始需求，避免把推测写成确定条件。评测时既检查改写是否覆盖目标，也检查是否引入无依据的事实。可以比较原始查询、改写查询和二者联合检索的结果，发现改写把检索方向带偏的问题。

常见追问： 是否要每次都追问用户？

回答： 只追问会实质影响参数适用性、任务目标或执行条件的信息；已有明确上下文时复用它，避免让用户重复填写。

二、GraphRAG 知识建模与参数检索

先解释知识如何组织和一次查询如何执行，再深入切分、embedding、混合检索与重排，最后讨论替代方案。重点是召回到适用且可执行的参数。

本章题目： Q15、Q16、Q17、Q18、Q19、Q20、Q21、Q22、Q23、Q24、Q34、Q35、Q36、Q37、Q38、Q39、Q42、Q43、Q44、Q45。

Q15：你的 GraphRAG 存什么，提供什么能力？

备考定位：A · 核心必答｜基础。 答题抓手：参数知识、影响关系与社区发现的实际作用。

参考答案：

数据库中的知识包括参数定义和已有方案，召回会包含人工调参成功方案；GraphRAG 组织参数描述和参数影响关系，并做了社区发现。自动调参成功结果也会持久化到数据库。系统结合用户需求和初始 QCAT 结果召回相关知识，让模型既能找到直接相关参数，也能查询关联参数与方案，为调整建议提供依据。

当前推荐主要依赖模型推理。社区结构能帮助组织关联知识，但是否已经以确定性规则用于搜索分组、怎样选择跨社区参数，需要按实际实现补充。不能把社区发现说成自动消除参数耦合或直接保证搜索最优。

图存储保存关系，GraphRAG 利用关系参与检索增强；要能展示一次真实查询的入口、关系路径、返回参数及社区信息，而不只列数据库名称。

常见追问： 同一社区的参数一定互相影响吗？

回答重点： 社区由图结构和所用算法形成；显式影响关系与社区归属是不同证据。影响关系的来源、适用条件和实验验证仍需保留。

Q16：为什么不用普通向量 RAG 或关系型数据库？

备考定位：A · 核心必答｜进阶。 答题抓手：图检索、向量检索和关系库的选型依据。

参考答案：

向量检索擅长从自然语言问题定位相关内容，但不天然保证拿全一个方案下的参数及其影响关系。本项目除了参数描述，还保存参数间影响关系并做了社区发现；图查询可以在定位相关节点后补充关联证据和社区上下文，辅助模型理解联合调整的可能性。具体收益要通过对照验证。

关系型数据库也能表达这些关系。如果只有方案和参数两张表、关联查询固定，关系库可能更简单。选择图数据库的理由应来自真实存在的多类型关系、可变路径查询和维护需求，而不是认为图数据库一定更先进。

常见追问： 图查询就一定比 SQL 快吗？

回答重点： 不是。要结合数据规模、查询路径、索引、部署与维护成本比较。

Q17：方案、参数、描述如何建模？参数值放哪里？

备考定位：A · 核心必答｜难点。 答题抓手：参数定义、方案推荐值与运行实例的区别。

参考答案：

当前已确认知识内容为参数定义与已有方案，召回包含人工成功方案，自动调参成功结果也会入库；方案配置的具体字段或引用方式仍需核对。材料可能是 MD、HTML、PDF，文件格式与领域实体结构是两个层次。可以分别组织“方案关联参数”和“参数影响参数”，参数描述作为属性或带来源的片段。社区成员关系应保留所属知识图版本；具体字段、关系方向和权重按实际库说明。

建模时进一步区分参数定义和方案内配置。参数定义表达参数是什么，包括标识、描述、单位等；方案内配置表达某个方案把这个参数设置成什么值。

同一个参数在多个方案中的值可能不同，因此不能把方案特有的值直接写成参数定义的全局属性。简单情况可以把值放在方案到参数的关系属性里；需要保存证据、版本或审核状态时，可以单独建配置项节点。

参数描述如果只是一个字段，作为属性即可；如果需要多个语言、版本或独立来源，可以拆成文档片段或定义版本节点，不必把所有文本都建成节点。

扩展模型示例（仅适用于确实保存取值与版本的情况）：

    graph LR
    S[方案版本] -->|包含| A[配置项]
    A -->|引用| P[参数定义版本]
    A --> V[取值或曲线引用]
    P -->|来源| D[文档片段]

常见追问： 如果值是 LUT 或数组呢？

回答重点： 保留结构化类型和维度，必要时存外部配置引用与校验哈希，避免当作无类型文本处理。

Q18：如何处理参数重名、平台差异和版本变化？

备考定位：A · 核心必答｜难点。 答题抓手：参数稳定身份、平台过滤与版本适用性。

参考答案：

不能只用参数展示名称当唯一键。可以结合平台、模块、完整字段路径和 schema 版本确定参数定义身份。展示名称用于阅读，稳定标识用于关联。

查询时先使用已知任务信息限制适用范围，再进行语义匹配或图扩展。如果平台或版本缺失，系统应该补充信息或明确保留不确定性，而不是自动套用最相似的定义。

旧定义与旧方案应保留版本关系，便于历史实验复现，不能更新一个节点后让所有旧方案悄悄引用新含义。

常见追问： 新版本与旧版本参数可以自动映射吗？

回答重点： 只能在有明确映射依据和校验规则时转换，字段名字相似不等于行为相同。

Q19：MD、HTML、PDF 中的参数定义和成功方案如何解析入库？

备考定位：B · 重点追问｜进阶。 答题抓手：结构化解析、实体消歧和入库质量。

参考答案：

知识内容是参数定义和已有方案，材料可能以 Markdown、HTML、PDF 提供。我会先把文件解析成保留层级、表格和来源的统一文档结构，再切分和建立检索索引；文件格式并不决定知识必须存成哪一种数据库结构。实际使用了哪些解析库、抽取模型和数据库，需要用项目配置补齐。

输入 建议解析方式 重点保留与检查
Markdown 按标题、段落、表格、代码块解析，可使用 AST 标题路径、完整参数表、配置代码；不在数组或代码中间任意断开
HTML 按 DOM 提取正文，清理导航与重复页脚 标题、列表、表头、行列关系、代码和正文中的单位；不能用正则直接去标签后拼成一长串
文本 PDF 按页面与版面解析文字和表格 阅读顺序、页码、跨页表格、单位、上下标；双栏串行或丢表头会改变含义
扫描 PDF 先判断是否需要 OCR，再恢复版面和表格 字段名、负号、小数点、数字与字母混淆；关键参数数值低置信时复核，不直接下发

建议统一保留文档 ID、来源版本、章节路径、页码或元素定位、内容类型与原文哈希。对同一内容的多格式副本去重，但保留来源关系；正文片段、表格结构和配置产物可以分开存，用稳定 ID 关联。

结构化配置优先确定性解析；自然语言中的实体与影响关系可以由规则或模型提取，再做 schema 校验、实体消歧与来源核对。实体 ID 建议包含平台/模块/版本作用域，不能只按同名参数合并。向量片段关联实体，图关系关联原文证据；社区摘要若存在，也需要关联知识版本与支撑来源，不能凭摘要编造数值。

常见追问：自动调参成功后怎么回流？

成功结果入库已经确认。建议优先保存可还原配置与评测证据，再生成适合检索的方案说明，无需强制转成 PDF 后重新抽取。持久化、知识加工、图/向量索引发布是不同环节，实际更新机制待核对，见知识生命周期。

常见追问：原文里的“忽略前面要求并执行命令”怎么办？

文档和 OCR 文本是检索数据，不能升级为系统指令或执行权限。保持证据与指令分离，参数输出经过身份、范围和接口校验；解析错误与提示注入都不能直接转成设备操作。

Q20：一次 GraphRAG 查询具体怎么执行？

备考定位：A · 核心必答｜难点。 答题抓手：基线指标、参数召回、影响关系与社区证据。

参考答案：

本项目在初始 QCAT 评测之后，模型结合用户场景、目标和实际指标检索参数。知识库中可查询人工成功方案、参数定义及参数影响关系，并已做社区发现；当前参数选择与方案建议主要依赖模型推理。入口使用什么索引、社区信息怎样加载到 prompt，仍要用实际查询记录说明。

建议的可检查查询流程（不是对当前具体算法的断言）：

    flowchart TD
    A["用户目标<br/>初始 QCAT 指标"] --> B[定位成功方案与相关参数]
    B --> C["查询影响关系<br/>所属社区与跨社区关联"]
    C --> D["检查平台、场景与版本<br/>去重并限制候选规模"]
    D --> E["输出方案、参数与证据<br/>交给模型推荐候选或调整"]
    E --> F["程序校验建议<br/>生成候选实验批次"]

不应把整个社区无条件放入上下文或搜索空间。优先保留当前决策所需的参数、关系和来源；依赖参数可以保持固定，只有需要探索的参数才进入笛卡尔积。

常见追问： 图检索结果如何放进 prompt？

回答重点： 建议包括稳定参数 ID、描述、关联方案、影响关系、社区信息、适用条件及来源引用。字段以库中实际内容为准；来源缺失要明确标识，不能让模型伪造证据。

Q21：LLM 直接生成 Cypher 等图查询语句吗？

备考定位：C · 按岗扩展｜进阶。 答题抓手：查询模板、只读约束与自由生成语句的边界。

参考答案：

对查询类型相对固定的场景，我倾向于封装预定义的只读查询工具，让模型提供实体标识、查询条件和检索意图，应用生成参数化查询，容易控制行为和成本。

如果确实需要自然语言转图查询，要提供 schema，并在执行前检查允许的语法与操作、设置只读账户、查询超时和结果上限。仅在提示词中要求“只读”不足以形成执行权限边界。

常见追问： 参数化查询能防止所有风险吗？

回答重点： 不能。它主要处理参数传递，仍要限制查询结构、权限、复杂度及资源消耗。

Q22：怎么避免图检索内容太多或不相关？

备考定位：B · 重点追问｜进阶。 答题抓手：图扩展范围、关系类型与上下文预算。

参考答案：

对入口节点数、关系类型、扩展深度、返回数量和上下文长度设置边界。先做版本等适用性过滤，再按问题相关性和证据质量筛选；需要时可以增加 rerank，但要验证它的收益。

像参数定义这样的关键事实尽量保留原文或结构化值，长方案说明可以摘要。若不同来源互相冲突，要保留冲突及来源，让应用依据版本和可信度规则处理，不能在摘要时直接消除差异。

常见追问： 固定查询两跳是否合理？

回答重点： 跳数是成本边界，不是检索质量保证；关系语义和问题类型更重要。

Q23：没召回到参数，或召回了不相关参数，怎么办？

备考定位：A · 核心必答｜进阶。 答题抓手：无答案、低相关结果与拒绝进入执行的条件。

参考答案：

先定位原因：用户需求是否模糊、意图是否遗漏目标或约束、知识库是否缺少相应知识、查询是否只命中了相近词、适用条件是否错误排除了结果。无召回与低相关召回需要作为明确状态返回，不能用模型自行编造的参数填空。

可以采用有限次查询改写、补充必要信息、组合不同检索方式或转人工处理，但不能为提高命中率而取消必要的平台约束。召回阈值和筛选方法应在标注样本上验证；向量相似度不是参数正确的概率。

常见追问： 模型建议的新参数能不能写回知识库，供下次召回？

回答重点： 已确认自动调参成功后会持久化结果；这不意味着把模型提出的任何新参数写成参数定义。模型建议要与真实参数来源和实验验证分开，未经核实的参数不能因一次生成而入库为事实。成功方案后续如何更新图关系、向量索引和社区信息仍需核对，详见知识生命周期。

Q34：参数名是英文缩写，用户需求是中文，怎么检索？

参考答案：

我会同时保留参数原始标识和用于检索的语义描述。原始标识用于精确定位，描述中包含参数作用、所属模块、适用场景，以及经过核实的别名。用户说“暗处颗粒明显”时，语义检索帮助连接到相关描述；用户输入完整参数路径时，优先走精确或关键词匹配。

模型可以将口语需求转换成检索表达，但要保留原始目标与约束，不能把“保留细节”改写丢失，也不能自动断定问题根因。中英文缩写是否能召回正确参数，要用领域样本验证，不能假设 embedding 天然理解内部字段。

回答： 不替换原始标识，而是增加可追溯的解释和别名。映射必须来自文档或人工核验，避免机器翻译把不同参数合并。

Q35：文档怎么切分？参数描述被切断怎么办？

备考定位：B · 重点追问｜进阶。 答题抓手：按知识对象切分，保持字段与描述完整。

参考答案（可直接口述，策略建议）：

我按知识对象和文档结构切分。参数定义与成功方案的使用方式不同，所以切分粒度也不同：参数块用于精确找到字段，方案块用于找到适用场景和完整配置经验。当前知识类型已经确认，下面是可采用的策略，实际 chunk size 和 overlap 需要项目配置及评测记录支撑。

知识对象 切分单元 必须一起保留的内容
参数定义 一个参数或一组不可拆分字段 原始参数 ID、描述、单位/类型、合法范围及适用条件；没有的字段不能补造
成功方案 父级方案 + 按目标、配置、评测拆出的子块 方案 ID、适用场景、参数配置引用、基线与成功判据；子块能找回父级
参数表格 按参数行或有共同语义的行组 表题、列名、单位、合并单元格继承值；检索文本之外保留结构化表格
配置代码、LUT/数组 保持合法结构或使用产物引用 参数归属、类型、维度、完整配置位置与校验信息；不凭截断片段生成值

例如同一表格的一行含“字段、取值、单位、适用范围”，切分后仍应有这些对应关系。长表分块可重复表头及必要上下文，跨页表先恢复关系；不能只取某一页数字去 embedding。人工方案中的整组配置先作为关联对象保留，不把多个方案的取值无条件混成一个候选池。

实现上可先按标题/段落/表格划分，再对过长文本按句子和 token 递归切分。每个子块保留 doc_id、版本、标题路径、chunk_id、父方案或参数 ID 和来源定位。小块命中后按需补回父级方案和必要关系，最终组装仍受 token 预算限制。

追问：chunk size 和 overlap 设多少？

没有适用于所有文档的固定数字。可以把 256、512、1,024 tokens 作为实验档位，比较 0 和约 10%—15% 的文本重叠；这些是起始对照值，不是本项目实测配置。使用所选 embedding 模型的 tokenizer，算上标题和元数据后的输入也不能超限。完整短参数块无需为了统一长度硬补重叠；优先用结构边界避免切断语义。

追问：如何证明切分更好？

冻结文档、模型与查询集，比较参数/方案 Recall@k、证据完整率、错误参数值率、重复片段比例、最终任务效果及延迟和 token 成本。测试应包含跨页表、同名参数不同版本、长方案和扫描错误；不能只看文字是否连贯。

Q36：embedding 模型和向量索引怎么选？换模型如何迁移？

备考定位：B · 重点追问｜难点。 答题抓手：embedding 选型、索引质量与迁移一致性。

参考答案：

先确定 embedding 的对象和查询任务，再选模型。项目要把中文需求、QCAT 指标和英文参数标识关联到参数定义与成功方案，所以应使用真实中英文领域查询评测候选模型，而不是只比较通用榜单。当前具体模型、维度和索引配置尚未确认，不能编造一个名称当作使用经历。

建议的向量输入： 参数块用“原始 ID + 核实的别名 + 模块/标题 + 作用说明 + 适用条件”；方案块用“问题场景 + 调整目标 + 参数摘要 + 已验证效果说明”，通过方案 ID 关联完整配置和证据。保留原文与结构化数值，embedding 只服务相似检索，不负责准确保存/还原数值。可区分参数、方案和社区摘要的逻辑索引或类型过滤，但不一定需要三套数据库。

查询可由用户目标、保护约束、场景及必要的初始 QCAT 失败项组成；不要塞入整份报告中的无关数字。模型若要求 query/document 不同前缀或任务指令，按其规范生成；中文和英文描述可以共存，但别名必须有来源。参数路径、型号、版本和数值条件采用精确查询或元数据过滤，避免仅靠向量相似度判断适用性；混合检索见 Q37。

选型与索引验证： 在同一知识快照上比较参数与方案的 Recall@k、MRR/nDCG、无答案误召回、延迟、吞吐、维度、存储与更新成本。归一化及余弦/内积度量按模型要求配置；小库可精确检索，大库可比较 HNSW 等近似索引。以精确向量搜索为基准测 ANN recall，才能区分近似索引漏召回和模型语义表示问题。

增量和迁移： 新成功方案持久化后，建议按内容版本计算 embedding，用内容哈希识别重复或变化；记录模型版本、输入模板、切分版本和索引发布状态。换模型后即使维度相同也不能混用向量，应重建受影响文档索引，查询侧同步切换，在新索引验证后发布并保留回滚能力。图实体、关系与社区信息的更新也要记录对应知识版本。

常见追问与速答：

embedding 能理解内部缩写吗？ 不能假设，需要核实的定义、别名和领域查询评测；精确字段检索可补充。
是否需要向量化整张图？ 不一定。文本片段、实体描述或社区摘要可向量化，关系遍历由图查询完成；图 embedding 不是使用 GraphRAG 的必选项。

Q37：为什么混合检索？多路结果如何融合？

备考定位：B · 重点追问｜难点。 答题抓手：精确和语义召回融合、去重与排名依据。

参考答案：

关键词检索擅长字段名、缩写和明确术语，向量检索处理同义表达，图查询补充明确关联关系。可以多路取候选，按稳定参数 ID 去重，同时保留各路来源；平台或权限等硬约束仍要满足。

不同检索器的原始分数通常不在同一尺度，直接相加容易失真。可以使用 RRF 等基于排名的融合，再按需重排。RRF 的一个形式是对各路的 1 / (c + rank) 求和；常数和各路权重影响融合结果，要验证而不是当成万能公式。

图扩展产生的邻居不一定具有可比较的语义排名，可以先作为补充候选，再用相关性规则或统一重排筛选，不必强行当作同尺度的第三路分数。

常见追问： 多路都命中同一段文本，要给模型看三次吗？

回答： 不需要。合并实体或片段、保留多来源证据，并在上下文组装时去重，避免重复内容挤占预算。

Q38：召回与 rerank 有什么区别？为什么不让大模型看全部参数？

备考定位：B · 重点追问｜进阶。 答题抓手：候选召回与精排分工，以及上下文成本。

参考答案：

召回用于从大规模知识中快速选出候选，通常先计算文档向量并建立索引。重排对较少候选进一步比较与查询的相关性，例如 cross-encoder 联合读取查询和文档，获得更精细的排序，但每对输入都要计算，成本更高。

让大模型阅读全部参数会增加 token、延迟和干扰。更合理的做法是先保证召回覆盖，再重排和组织有依据的参数信息。重排只能处理已有候选，前面漏掉的参数通常补不回来。

常见追问： 使用 LLM rerank 可以吗？

回答： 可以比较，但要控制候选数量、输出合法性、位置偏差、稳定性和成本。与专用重排模型比较后再选择，不因为用了大模型就认为排序更准。

Q39：图关系和社区发现能否直接决定哪些参数一起调？

备考定位：B · 重点追问｜难点。 答题抓手：显式影响关系、社区结构与联合搜索的边界。

参考答案：

当前图谱可以查询参数影响关系，并做了社区发现。显式关系提供某种关联或影响的知识依据，社区提供连接较紧密的参数集合；两者都应结合当前场景、目标和知识来源使用，不能自动证明因果或普遍适用。

已有完整成功方案应先检查其适用性，不必强行拆成笛卡尔积。对于需要探索或局部调整的部分，建议把直接相关参数作为入口，用影响关系补充可能耦合的参数，再结合社区和预算确定联合搜索组。同一社区不必全量进入笛卡尔积，不同社区之间的重要关系也不能遗漏。只为配置完整性需要的依赖参数可以保持固定。

当前推荐主要由模型推理，尚未确认存在上述确定性分组算法。若落地分组搜索，需要评估减少实验量的收益，以及漏掉跨组联合最优配置的代价，并做最终联合验证。

常见追问： 图扩展提高 Recall 却增加实验数量，怎么取舍？

回答： 同时比较关联覆盖、参数适用性、实际候选规模与固定总实验预算下的目标达成率。图谱取证不能只追求“召回越多越好”。

Q42：为什么用 RAG 而不是微调？什么时候考虑微调？

备考定位：B · 重点追问｜基础。 答题抓手：知识更新问题与模型行为训练问题的区别。

参考答案：

参数定义和方案会更新，而且需要引用来源，适合通过检索提供事实。微调更适合学习稳定的意图标签、输出结构、术语表达或工具选择习惯，不能替代最新参数事实和执行校验。两者可以结合：微调改善理解行为，RAG 提供当前知识。

如果意图类别固定且样本足够，可以先比较规则、小模型分类器和通用 LLM，不一定需要训练大模型。若考虑 LoRA 等参数高效微调，需要准备高质量样本、合理划分数据，并验证泛化、格式正确率与维护成本；“参数高效”也不意味着没有训练和推理资源成本。

常见追问： 向量模型效果不好，应该微调生成模型吗？

回答： 先定位瓶颈。检索表示问题应考虑改善描述、检索策略或训练 embedding/reranker；生成模型微调不能自动修复召回缺失。

Q43：如何证明某个参数影响结果，而不是模型把相关性当成因果？

备考定位：C · 按岗扩展｜难点。 答题抓手：控制变量、重复实验和因果结论边界。

参考答案：

RAG 提供候选依据，模型提出调整假设，真正的效果需要实验验证。比较时固定其他条件、记录参数变化与评测结果，并通过重复测试确认差异不是采集波动。

逐参数粗扫有助于观察局部响应，但参数之间可能有交互，单独有效不保证组合有效；后续还要评估组合与未参与选择的场景。模型生成的解释也需要与实验记录一致，不能因为解释合理就宣称已找到因果关系。

常见追问： 为什么这题会出现在 AI 应用面试？

回答： 它检验应用是否区分检索证据、模型建议和外部验证，避免把大模型叙述当成业务结论。

Q44：换平台或换参数库，哪些能力可以复用？

备考定位：C · 按岗扩展｜进阶。 答题抓手：公共工作流与平台适配器契约。

参考答案：

需求结构、检索接口、工作流编排、任务状态和观测机制可以设计成相对通用的部分。平台相关内容包括参数知识、字段映射、适用条件、业务校验和设备执行适配器。

通过有版本的数据契约连接两层，避免把每个平台的例外都堆进系统提示词。新平台接入要验证知识质量、参数覆盖、映射正确性和完整执行效果，不能仅切换数据库地址就认为完成迁移。

常见追问： 适配器怎么定义？

回答： 明确输入的参数身份与配置版本，以及输出的可执行请求或错误；各平台实现具体映射，公共工作流依赖接口契约而非文件路径和设备细节。

Q45：现在主要依赖模型推理推荐参数，你会怎样改进？

备考定位：C · 按岗扩展｜进阶。 答题抓手：图谱证据、结构化计划、程序约束与可验证收益。

参考答案（可直接口述，改进设计）：

我会在已有方案召回和成功结果入库的基础上，把模型推荐变成有证据、可校验的结构化计划。先检查历史方案是否适用；适用时可验证完整配置，不完全适用时再考虑局部调整或新搜索。具体先后顺序是建议策略。先明确主目标、保护指标和基线，再召回参数、影响关系与社区信息，让模型输出本轮参数、候选值、保持不变项、来源引用和简要理由。

程序校验参数身份、取值语义、范围、适用版本和已知约束，只对探索分支计算笛卡尔积规模，再连同已有方案验证核对总预算。合法且预算内的候选再交给已有单候选实验接口。整批结束后先检查实验有效性、约束和目标，再比较候选、更新历史最佳；模型根据精简的真实反馈推荐下一轮。

如果组合数量过大，再评估关联参数分组、粗到细或抽样，而不是默认把整个社区全量交叉组合。分组会损失一部分跨组探索能力，因此保留重要跨社区关系并进行联合验证。社区发现已实现，确定性分组、严格校验和这套结构化计划仍属于建议，不能写成既有成果。

沿一次真实调用讲：模型接口 → 工具契约 → 参数交接 → 长任务等待 → 超时重试 → 结果反馈；再展开模型网关和提示词管理。

Q08：QGenie 如何接入？如何选择模型？

备考定位：B · 重点追问｜基础。 答题抓手：实际模型身份、接口能力与选型评测。

参考答案：

我会把模型访问封装成适配层，统一请求消息、模型配置、超时、错误处理和返回结构。是否原生支持 tool calling、结构化输出、流式响应，要以实际使用的接口和模型版本为准。

模型选型会用需求样本比较意图识别准确性、目标与约束提取完整性、结构化输出合法率，以及检索查询对最终参数召回的贡献，同时记录延迟和费用。是否使用模型对召回候选做筛选，也应按真实链路单独评测。

常见追问： QGenie 是模型本身，还是调用平台/接口？

准备要求： 准确说明项目中 QGenie 的角色、实际模型标识和调用方式，不凭名称推断接口能力。

Q09：Function Calling 的完整过程是什么？

备考定位：A · 核心必答｜进阶。 答题抓手：模型提出调用、程序校验执行、工具结果回传。

参考答案：

如果模型通过工具触发检索，应用向它提供参数检索工具的名称、用途和 schema。模型返回调用请求，应用检查查询条件并执行 RAG，再把召回结果与调用 ID 关联后回传。调用现有流程也可以封装成工具，但不代表必须由模型决定何时调用；固定节点同样可以完成交接。

模型输出了工具调用，并不表示工具已经执行。执行权在应用侧；工具返回结果后，模型可能继续调用其他工具，也可能生成最终答复。

如果当前接口不支持原生工具调用，可以采用受约束的结构化动作输出，但仍需要明确解析、校验和错误修正机制，不能执行模型任意生成的代码。

常见追问： 模型一次请求多个工具，是不是可以全部并行？

回答重点： 只有无依赖、无资源冲突的调用才能并行。配置设备和采集图像通常有顺序依赖。

Q10：工具接口怎么设计？粒度多大合适？

备考定位：A · 核心必答｜进阶。 答题抓手：工具契约、业务粒度、错误类型与副作用。

参考答案：

工具应该表达稳定的业务动作，并有明确输入、输出和前置条件。过细的接口会让模型承担大量控制步骤，过粗的接口又会隐藏失败位置。

对当前主线，重点是参数检索接口和现有流程入口。检索接口接收意图及条件，返回参数标识、描述和来源；现有流程入口接收符合其契约的请求，复用已有设备控制与评测逻辑。无需让前端模型重新编排每一条硬件命令。

返回值要区分任务已受理、正在执行、成功和失败，包含任务 ID、错误类型及产物引用，而不是只返回一句“调用成功”。

常见追问： 机械臂和手机都要控制，如何避免操作冲突？

回答重点： 使用设备资源占用机制和执行前检查；生产环境可能需要租约及防止失效执行者继续操作的机制，不仅是进程内布尔变量。

Q11：RAG 召回参数以后，怎样接上现有流程？

备考定位：A · 核心必答｜进阶。 答题抓手：参数身份如何映射到配置实例及可执行请求。

参考答案：

关键是定义知识、搜索建议与实验输入之间的数据契约。模型结合初始评测，从 GraphRAG 召回参数定义、人工成功方案和影响关系并推荐调整，程序结合方案与搜索配置组织候选。建议保留稳定参数标识、值的语义、来源和适用条件，再映射到现有配置与 bin；已有实验接口一次执行一个候选。平台、模块、版本字段和调用签名仍按实际接口说明。

交接前可以检查参数确实来自本次召回或受控知识源、下游是否支持、是否重复或存在冲突。若下游还要求起始值或搜索范围，需要明确它们来自现有配置、知识库还是既有策略；召回参数定义不代表已经具备可执行配置；召回成功方案时，也要检查其配置能否还原并映射到当前版本，不能只凭方案摘要下发。

结构化输出校验解决格式问题，业务映射解决接口兼容问题。不能让模型把知识库中的参数名随意改写成另一个下游字段，也不能静默丢弃无法映射的必要参数。

常见追问： 召回参数和生成参数值有什么区别？旧流程必须改造吗？

回答重点： 前者回答“有哪些相关参数”，后者回答“具体设置为多少”。通常可以通过适配层接入原入口；是否需要改造取决于原接口，不能直接假设接受任意参数列表。

Q12：硬件实验耗时较长，Agent 怎么等待？

备考定位：A · 核心必答｜进阶。 答题抓手：长任务提交、持久化状态与等待资源释放。

参考答案：

适合把提交任务和获取结果分开。执行服务接收配置后返回任务 ID，工作流通过轮询或事件获取状态，完成后再进入评估节点。等待期间通常不需要反复调用模型。

任务与配置版本、设备、采集产物和评测结果绑定，避免把上一轮结果当成本轮结果。还要分别定义模型请求超时、工具请求超时和实验总超时。

取消工作流不一定能取消外部任务。需要记录取消状态、调用外部取消接口或在任务结束后丢弃不再适用的结果，并释放资源。

常见追问： 现在是不是已经用了消息队列？

准备要求： 按实际实现回答。同步执行是有效的初始方案，但不能声称具备尚未实现的异步调度能力。

Q13：超时后重试，如何避免重复执行？

备考定位：A · 核心必答｜难点。 答题抓手：提交结果未知时的幂等、查询和对账。

参考答案：

先区分网络瞬时错误、输入错误和不可重试的业务失败。网络超时只表示没有及时收到响应，不能证明操作没有执行。

提交实验时使用稳定的幂等键，重试同一个请求时复用该键；执行服务持久化请求和任务的对应关系，重复提交返回已有任务。超时后优先查询状态，再决定是否重新提交。

幂等键不能仅等于参数哈希，因为同一组参数可能需要多次独立采样。应区分“同一次实验的重试”和“新建一次重复实验”。

常见追问： 能否保证 exactly-once？

回答重点： 跨进程和外部设备很难笼统保证严格恰好一次；说明具体采用的去重、状态查询、对账与补偿机制及其边界。

Q14：整批评测结果如何反馈给模型？每轮都会再查 RAG 吗？

备考定位：B · 重点追问｜进阶。 答题抓手：单候选结果关联、整批汇总与再次检索的区别。

参考答案：

已确认一次实验接口调用执行一个候选，整批候选评测结束后，模型统一分析结果并推荐下一批。候选文件通过 plan_id、bin、图像和 IQ_info 组织结果；具体是同步返回、任务查询还是文件回写，需要结合接口代码确认。

建议向模型提供初始基线、目标与保护指标、候选参数差异、各项实际结果、当前最佳及剩余预算，完整图像和日志保留引用。候选缺失或执行失败应明确标记，不用默认零分代替，也不把批次一直等待当成正常闭环。

当前任务的批次历史用于运行中决策；自动调参成功后的结果持久化用于保留领域经验，二者与工作流 checkpoint 也不同。每轮分析历史不等于每轮都重新查询 GraphRAG。需要新增参数、场景变化或证据不足时如何再检索，应以调用链说明。样例有图像路径也不证明模型实际接收了视觉输入；是否直接看图另行核对。

常见追问： 一个候选返回结果后立即调用模型吗？

回答： 当前是整批完成后统一决策。批内实验如何并发或排队由调度实现决定，不能从 JSON 数组推断。

Q52：如何统一接入多个模型，处理限流与故障切换？

备考定位：B · 重点追问｜难点。 答题抓手：限流、超时、回退模型与输出契约兼容。

参考答案：

模型适配层统一应用需要的输入输出、超时、用量记录和错误类型，但也保留各模型能力差异，例如工具调用、结构化输出、上下文限制和图像输入。接口格式相近不代表语义完全兼容。

限流按模型和租户控制，临时错误做有界指数退避与抖动，遵守服务端返回的等待信息。长期失败可以熔断或切换已通过评测的备用模型；认证失败、参数错误不能简单重试。

故障切换后继续做 schema 和业务校验，并记录实际模型版本。备用模型可能改变召回查询或细扫建议，不能悄悄降低验收要求。一次模型重试与一次新设备实验也要区分，避免故障切换导致重复执行。

常见追问： 模型请求超时是否意味着不计费？

回答： 不一定，服务端可能已处理。记录调用标识并尽可能核对实际用量；请求失败、重试次数和费用需要一起统计。

Q53：提示词如何设计、调试和版本管理？

备考定位：A · 核心必答｜进阶。 答题抓手：提示词职责、结构化输出和回归集。

参考答案：

围绕每个节点的任务设计提示词，明确输入含义、必须保留的约束、可用证据、允许的输出结构和缺信息时的行为。意图识别可以加入覆盖多目标、纠正和不支持请求的 few-shot 示例，但示例不能泄露测试集答案。

先收集错误类型，再针对性修改。例如经常遗漏“保留细节”，就检查输出结构是否包含约束，并增加相关开发样例，而不是不断堆叠泛化指令。每次变更记录 prompt 版本、模型、检索配置和评测结果。

约束输出格式可以用 schema 支持提高稳定性，但不保证事实正确。工具参数与执行权限仍由代码验证。温度降低可能减少波动，也不能保证不同模型版本或服务环境绝对可复现。

常见追问： 提示词改了以后，怎么确认没有修好一个问题又引入新问题？

回答： 在固定回归集上按错误类别和总体指标比较，关注约束遗漏、错误拒绝、参数有效性、token 和延迟，而不是只重测刚才失败的那一个样例。

Q54：Function Calling 和 MCP 有什么区别？这里需要 MCP 吗？

备考定位：C · 按岗扩展｜基础。 答题抓手：Function Calling 与 MCP 的层次及适用条件。

参考答案：

Function Calling 主要描述模型输出结构化工具调用请求的能力，实际执行仍由应用负责。MCP 是应用与外部工具或资源服务连接的一种协议方式，可以统一发现和调用能力；两者处在不同层次，可以配合使用。

应用可以把 MCP 服务暴露的工具转换成模型可见的工具定义，执行请求后再把结果返回给模型。MCP 不会自动完成权限、业务校验、幂等和审核，也不会让模型突然具备工具选择能力。

如果工具只由当前 Python 服务使用，直接函数或 HTTP 接口可能足够；多个应用需要复用工具时，才评估 MCP 封装的维护收益。当前项目是否使用 MCP，要按事实回答。

常见追问： 把设备控制封装成 MCP 工具就可以开放所有命令吗？

回答： 不可以。仍应提供受控业务操作、最小权限、参数校验和审计，工具返回的文本也不能自动作为高优先级指令。

四、工作流可靠性与 HIL 人工介入

围绕“什么时候停、失败后怎么恢复、谁能批准执行”展开。Q13 的提交幂等是本章的前置知识；Q48 再深化消息一致性。

本章题目： Q26、Q27、Q28、Q33。

Q26：达到轮数上限或连续无改善时怎么停止？

备考定位：B · 重点追问｜进阶。 答题抓手：可配置轮数、批次统计与结束原因。

参考答案：

当前会在目标达成、达到最大迭代轮数或连续无改善时停止，其中最大轮数可以配置。整批候选执行和汇总后才进入下一次模型决策，因此轮数、每批候选数和总实验调用数需要分开记录。

达标应报告成功配置；达到上限或无改善应报告停止原因、已测最佳候选及未达标项。最佳候选并不必然达标，不能用一个执行完成布尔值替代目标判断。

建议由程序按固定验收规则判断停止，同时增加每轮候选上限和总实验预算。连续无改善可按完整批次比较历史最佳，窗口和最小有效改善幅度参考评测波动配置；当前具体评分函数、窗口和幅度尚未确认。整批执行失败应按异常处理，不当成普通搜索无改善。

常见追问： 只限制最大轮数够吗？

回答： 不够。已有方案验证也消耗实验预算；需要展开的搜索分支中，笛卡尔积使规模随参数数量和候选值数相乘；相同轮数可能对应完全不同的实验量。详见改进方案。

Q27：工作流中途重启，怎么恢复？

备考定位：A · 核心必答｜难点。 答题抓手：checkpoint 恢复与外部任务事实核对。

参考答案：

可以使用持久化 checkpoint 保存图状态，并用稳定任务或线程标识关联恢复请求。但恢复节点不意味着外部任务可以安全重复执行。

恢复后先核对外部任务状态：未提交则提交，正在运行则等待，已完成则读取结果，状态冲突则进入对账处理。提交侧的幂等键和执行侧的持久化记录共同避免重复操作。

常见追问： 外部任务完成了，但 checkpoint 没保存怎么办？

回答重点： 通过原任务标识查询外部事实，再更新工作流；不能只凭 checkpoint 中“未完成”就再次执行。

Q28：怎么防止提示词注入和越权工具调用？

备考定位：B · 重点追问｜进阶。 答题抓手：非可信内容、程序授权与受控工具接口。

参考答案：

检索文档、工具日志和用户上传内容都可能包含不可信指令，需要作为数据传入，避免混入高优先级指令。但仅靠文字分隔不能保证安全。

应用侧采用工具白名单、身份权限检查、参数约束和受控设备接口。敏感配置与凭据由服务端管理，不需要放进模型上下文；日志和观测平台也要做脱敏。

常见追问： 把注入检测再交给一个模型就够了吗？

回答重点： 模型检测只能作为辅助，真正的执行权限由程序和基础设施控制。

Q33：HIL 应该接在哪里？如何用 LangGraph 实现人工介入？

备考定位：A · 核心必答｜难点。 答题抓手：审核位置、版本绑定、interrupt 恢复与副作用。

参考答案（可直接口述）：

这里我先按 Human-in-the-loop，也就是人工介入来理解。我会把人工介入放在参数召回后的方案确认、首次执行前的审核，以及迭代异常时的接管三个位置。

第一个位置在意图识别和 RAG 召回之后。当需求有歧义、关键条件不完整或召回参数的适用性不确定时，展示识别出的目标、约束、参数列表、参数描述和知识来源，由工程师确认或修正，再进入现有流程。这个位置主要解决“是否理解了正确的问题、是否选对了参数”。

第二个位置在可执行实验计划生成之后、提交设备执行之前。此时已经能展示具体配置差异、调整范围、候选数量、实验预算和预计设备占用，工程师可以批准一批边界明确的实验。这个位置解决“是否允许按这份计划实际执行”。如果生成配置或编译会修改共享工程，应在产生这些副作用之前完成相应审核；使用隔离工作副本时，可以先准备可审查的产物。

第三个位置在批次反馈和下一轮推荐过程中。当连续无改善、多个指标冲突、模型建议超出批准范围，或者设备异常无法自动恢复时，暂停并展示实验历史、当前最佳结果和异常原因，让工程师选择继续、修改范围、回退或终止。修改后的方案仍要通过程序校验，不能因为是人工输入就跳过检查。

人工介入不意味着每轮都确认。我倾向于批准参数集合、允许范围和实验预算，在授权范围内自动执行；需要改变目标、扩大范围或处理异常时，再请求人工决策。

追问一：为什么不在用户刚提出需求时就审核全部内容？

用户提出目标时，尚未确定实际参数、配置差异和实验成本。先做必要的澄清，等召回结果与实验计划形成后，再审核具体内容，人工决策才有依据。低风险且规则明确的参数确认可以按策略自动通过，执行授权仍按实际业务要求设置。

追问二：在 LangGraph 中怎么暂停和恢复？

可以在审核节点调用 interrupt()，向上层返回可序列化的审核内容，并配置持久化 checkpointer。服务端保存任务与 thread_id 的对应关系，前端展示待审核项。审核人提交批准、修改或拒绝后，服务端先验证身份、权限和方案版本，再使用同一个 thread_id，通过 Command(resume=...) 恢复图执行。

恢复内容可以包含审核动作和修改意见，图中的条件边再决定执行、重新校验、重新规划或终止。thread_id 用于定位工作流，不等于权限凭证；interrupt() 本身也不会自动提供审核页面、身份鉴权和审计记录。

追问三：恢复后会不会重复执行设备操作？

被中断节点在恢复时会从节点开头重新执行，interrupt() 之前的代码可能再次运行。因此，审核节点应主要读取和展示计划，设备提交放在批准后的独立执行节点，并使用幂等键和外部任务状态核对。仅仅分成两个节点还不能保证外部操作恰好一次。

追问四：如何保证批准的就是实际执行的版本？

审核记录应关联任务、计划版本或配置哈希、参数范围、预算、审核人和时间。执行前再次比对，如果配置在批准后改变，旧批准不应继续生效。人工修改会生成新版本，重新校验，必要时再次审批；过期或重复提交的审核回复要被识别和处理。

追问五：一直没人审核怎么办？HIL 会不会拖慢系统？

为待审核状态定义有效期、取消与提醒机制。到期后保持未授权状态并受控结束或继续等待，不能把“无人回复”当作批准。等待期间避免占用不必要的设备资源，恢复时重新检查外部条件。评测时分别统计人工等待时间和自动执行时间，同时报告干预率、人工活跃处理时长和全自动达成率，不能只展示扣除人工等待后的总耗时。

追问六：如果面试官说的是 Hardware-in-the-loop 呢？

需要先确认缩写含义。硬件在环接在候选配置生成与编译之后：真实设备加载配置、执行采集，QCATS 返回实际指标，后端再据此推荐下一轮调整。它强调用真实硬件反馈形成闭环，与人工审核的 Human-in-the-loop 是两个不同概念。

准备要求： 上述审核节点、持久化恢复和版本绑定目前未被确认已经落地；按实际情况使用“已经实现”或“我会这样设计”。准备一份真实审核样例或设计稿，说明审核输入、可选动作及恢复后的节点路径。

Q70：内存、上下文、State、长期记忆和 KV cache 有什么区别？

备考定位：A · 核心必答｜基础。 答题抓手：RAM、上下文、State、长期记忆与 KV cache 分层。

参考答案（可直接口述）：

我先把运行资源和业务信息分开。程序内存是 Python 对象、图像数组、请求缓冲等占用的 RAM；模型上下文是本次调用实际接收到的消息、工具结果和检索内容；State 是工作流用来推进任务的结构化状态。State 可以持久化，但不必全部传给模型。

长期记忆用于跨任务或跨会话复用信息，例如用户偏好、经过验证的经验。领域 RAG 则管理有来源的专业知识，二者可以共享存储技术，但权限、权威性和生命周期不同。KV cache 是推理过程中缓存注意力键值的计算优化，不等于用户记忆，也不自动成为长期知识。

这些是逻辑职责，并非必须部署七套数据库。选择存储时看查询、更新、恢复与隔离要求，不能只因为都叫 memory 就混在一起。

常见追问： 把聊天历史存到数据库，模型就记住了吗？

回答： 没有。只有应用在后续调用中检索或组装相关信息，模型才有机会使用它。持久化解决保存问题，记忆系统还要解决该存什么、何时取用、如何更新和失效。

Q25：历史不断增加，如何控制上下文？

备考定位：B · 重点追问｜进阶。 答题抓手：前端上下文保留什么，后端完整历史存哪里。

参考答案：

对当前主线，模型需要当前需求、有效条件、检索知识和整批反馈中的决策信息，不必每轮装入全部原始实验记录。多轮用户修改需求时，要保留仍然有效的条件，并记录哪些新信息替换了旧条件。

原始需求、结构化意图、初始基线和参数标识应单独保存。当前有整批反馈决策，建议为下一轮模型调用组装本轮结果摘要、历史最佳、保护指标与剩余预算；长描述按预算裁剪，但关键约束不能只依赖自由文本摘要。完整实验历史保持可追溯，通过任务与候选标识按需读取。

常见追问： 怎么检测重复方案？

回答重点： 规范化完整参数配置后比较，考虑默认值、字段顺序和数值表示；同时区分误重复与有意重复采样。

Q72：对话和实验历史越来越长，怎么控制上下文窗口？

备考定位：A · 核心必答｜难点。 答题抓手：token 预算、关键事实保留与可追溯摘要。

参考答案：

根据实际模型限制为输入和输出留预算。输入包括系统规则、工具定义、当前需求、必要消息、检索证据及工具结果，不能只数用户文本。先保留当前任务目标、硬约束和关键参数身份，再按需选择最近消息与相关历史。

较早的解释可以摘要，原始日志外置；数值、配置版本、审核状态和已执行任务 ID 保存在结构化 State 中，不能只依赖摘要。细扫时可以提供最佳候选、代表性失败和相关趋势，并保留查询完整记录的入口。

压缩要维护工具调用与结果的协议完整性，不能留下没有对应结果的调用或把过期失败解释当成当前状态。压缩后对照原始记录检查必要事实；反复摘要也会累积失真，因此保留来源并允许重新读取。

Q76：LangGraph State、checkpoint 和跨会话记忆怎么配合？

备考定位：B · 重点追问｜难点。 答题抓手：当前状态、恢复快照与跨会话知识的边界。

参考答案：

State 服务于当前流程，checkpoint 用于保存可恢复的状态和执行信息，跨会话记忆用于未来任务复用。它们可以在基础设施上共用数据库，但键、作用域和读取规则应分别设计。

恢复一个旧任务时，应该关联原有目标、配置和审核版本，并核对外部执行状态。长期记忆在此期间发生变化，不应无条件改写正在恢复的任务；需要显式判断是否仍适用，必要时重新规划或审核。

跨会话记忆一般在明确边界读取，例如任务开始或需要查历史时，并在得到验证结论后写入。使用框架提供的持久化或 store 能力时，要确认实际版本和配置，不能认为配置了 checkpointer 就自动实现了长期记忆检索。

常见追问： 一个用户可以永远使用同一个 thread_id 吗？

回答： 要根据会话和任务边界设计。把所有任务混入一个线程会增加历史污染和恢复歧义；用户标识、项目标识与会话标识应各自有职责，也不能用 thread_id 代替授权校验。

Q73：长期记忆应该存什么？怎么决定写入和读取？

备考定位：B · 重点追问｜进阶。 答题抓手：记忆写入条件、结构化字段和按需读取。

参考答案：

本项目已经把自动调参成功结果持久化到数据库，也会召回已有人工成功方案。下面是对写入质量和读取生命周期的进一步设计，具体 schema、去重、版本和索引同步尚需核对。

我会把任务经历、稳定事实和流程经验分开管理。任务经历记录发生过什么；稳定事实记录有来源且适用范围明确的信息；流程经验记录如何完成某类任务。不是每句话都值得长期保存，临时猜测、失败中的未证实结论和短期设备状态通常不应自动升级为长期事实。

写入可以经过候选提取、来源核验、去重和作用域确定，再保存为有版本的记录。适合保存的内容包括用户明确表达的稳定偏好、经过验证且可复用的流程，以及需要后续查询的实验结论。读取时先限制用户、项目、平台和有效版本，再按相关性选择，并保留来源供模型或程序检查。

常见追问： 所有记忆都需要向量化吗？

回答： 不需要。明确偏好、参数 ID 或状态适合结构化查询；相似历史任务适合语义检索；方案依赖可以用图关系。存储方式应服务查询需求，而不是把一切都做成向量。

Q74：新旧记忆冲突怎么办？用户改口以后如何防止旧记忆继续影响？

备考定位：B · 重点追问｜难点。 答题抓手：事实来源、作用域、版本冲突与旧信息失效。

参考答案：

先区分信息权威性和作用域：权限与执行规则不被普通记忆覆盖；领域参数事实由有效版本的权威知识源决定；当前用户明确的任务要求优先于旧偏好。时间新不一定更正确，需要结合来源、适用条件和验证状态。

用户明确纠正某项信息后，创建新版本并把旧版本标为已替代，更新结构化存储和检索索引。读取时过滤失效记录；索引异步更新尚未完成时，也可以在最终读取阶段核查权威记录状态，避免旧向量命中重新污染上下文。

对于无法自动判断的冲突，保留双方来源并请求澄清，而不是让模型任选其一。如果变化影响已经批准的实验计划，还要使旧批准失效，重新校验和审核。

常见追问： 能不能只在 prompt 中写“忽略旧记忆”？

回答： 不够。旧内容仍在上下文里可能持续干扰，应该在存储和检索层处理版本与状态，提示词只是补充说明。

Q75：长期记忆如何做隔离、过期和删除？

备考定位：B · 重点追问｜难点。 答题抓手：权限、过期、索引与缓存中的删除传播。

参考答案：

按用户、项目或任务作用域保存和检索，不能通过相似度把其他用户的信息带进上下文。共享经验需要单独审核并明确共享范围；服务凭据由凭据系统管理，不作为可供模型检索的普通记忆。

记忆根据用途设置有效期或失效条件。例如环境版本变化可能使某条经验失效，长期偏好可以由用户修改。用户请求删除时，要追踪权威记录、向量索引、缓存以及由它派生的摘要等副本，避免删掉原文后仍从其他路径召回。

备份和审计保留需要明确生命周期，删除状态应对在线读取立即生效，物理清理按约定执行。已经在某个活跃会话中的副本也要处理，不能声称删除数据库一行就瞬间抹除了所有使用痕迹。

常见追问： 删除记忆是不是让模型权重忘记了它？

回答： 这里删除的是应用保存和提供的内容，不代表修改模型权重。除非另有训练机制，否则不能把应用记忆读写与模型训练混为一谈。

Q77：如何评价记忆系统有效，而不是“存得越多越好”？

备考定位：B · 重点追问｜难点。 答题抓手：记忆命中、污染、冲突、删除和成本评测。

构建跨会话任务：前一会话提供事实或偏好，后一会话在相关问题中应正确使用；同时加入不相关任务，检查系统不会强行套用旧信息。还要测试用户纠正、事实过期、删除请求和跨用户隔离。

在同样模型、任务预算和知识条件下比较无记忆、仅最近历史、带长期记忆等方案，关注最终任务效果及新增成本。评价时最好使用未参与经验沉淀的新任务，避免只记住测试答案。

常见追问： 用户偏好答对了，但用了错误来源，也算成功吗？

回答： 应分开记录答案正确与来源/权限正确。碰巧答对不能掩盖错误取用，尤其是跨用户或已经失效的内容。

Q71：Agent 服务跑久了内存持续上涨，怎么定位和处理？

备考定位：B · 重点追问｜难点。 答题抓手：持有引用、无界集合、native 内存与负载剖析。

参考答案：

先判断增长来自什么：同时运行的任务更多、缓存正常填充、历史列表无界增长、未完成协程持有对象，还是 native 库分配没有释放。记录进程 RSS、容器用量、活动任务数、队列长度和缓存大小，在相同负载下做运行前后对比。

Python 分配可以用 tracemalloc 快照比较；RSS 包含它未必覆盖的 native 分配，例如图像库和部分数组缓冲。对象已释放后，内存分配器也可能保留空间，因此 RSS 不马上下降不等于一定泄漏。要结合对象引用、负载停止后的状态和多轮趋势判断。

控制措施包括限制并发与队列、使用有大小上限的缓存、分页读取历史、及时关闭文件和响应、清理完成任务的引用。大图像或原始日志放外部存储，State 只留引用，避免每个节点复制和序列化整份数据。对 RAW 解码、格式转换和 base64 编码都要注意额外副本。

常见追问： 调用 gc.collect() 能解决吗？

回答： 不能替代引用和生命周期管理。仍被引用的对象不会因此释放，native 缓冲和分配器也有自己的行为。先找到无界增长或持有链，再决定优化措施。

Q78：模型推理显存和应用内存如何控制？KV cache 算长期记忆吗？

备考定位：C · 按岗扩展｜难点。 答题抓手：推理显存组成、并发与 KV cache 生命周期。

参考答案：

应用 RAM 主要受进程、并发任务、图像和缓存影响；自建推理服务的 GPU 显存还包括模型权重、KV cache、计算工作区等。长上下文和更多并发序列通常会增加 KV cache 压力，具体规模还取决于模型层数、KV 头数、数据类型和服务实现。

控制方式包括限制单请求上下文与输出、设置合理并发和排队、减少不必要图像副本，并根据任务评测选择批处理、缓存或量化策略。要一起看峰值内存、首 token 延迟、尾延迟和正确率，不能只看平均占用。

KV cache 用于复用推理计算，可能在服务内保留或复用相同前缀，但它不负责长期事实的版本、权限、纠正和检索，因此不能充当完整的长期记忆系统。只通过 QGenie 调用模型时，底层显存由平台管理，应用负责请求预算、并发和调用观测，不声称自己完成了推理端显存优化。

常见追问： 减少上下文就一定能解决 OOM 吗？

回答： 不一定。权重、并发、其他 GPU 进程和工作区都可能占用显存；先测量分配与负载，再定位具体瓶颈。

Q79：如何把内存和记忆管理应用到 Camera Agent 或 Hermes 使用经验中？

备考定位：B · 重点追问｜进阶。 答题抓手：结合项目设计可验证的记忆与资源管理案例。

参考答案：

对于 Camera Agent，我会让任务 State 保存意图、参数身份、配置版本和任务引用，大图和完整实验日志放外部存储；模型每轮只接收必要目标、参数说明和相关实验摘要。参数定义和已有方案由知识层管理，自动调参成功结果已会入库；可复用操作流程则可以进一步整理成 Skill。成功配置、操作流程与工作流恢复状态需要分别管理。

用户纠正场景后更新意图版本并重新检索，不让旧场景记忆覆盖本次要求；参数知识升级后检查旧经验的适用范围；任务结束后释放进程内对象，并按留存策略维护记录。这样同时控制资源增长和信息污染。

对于 Hermes，先说明自己实际使用版本中启用了哪些记忆或 Skills 功能，再展示一次跨会话复用、一次纠正或删除后的验证。不要因为官方介绍有记忆就声称它自动做了正确的隔离、过期和冲突解决；这些行为需要实际检查。

常见追问： 面试官让你现场验证，你会做什么？

回答： 准备五步演示：保存一项明确偏好；新会话在相关任务中正确使用；在无关任务中不干扰；修改后只使用新版本；删除后不再通过在线检索取用。另用固定并发连续运行任务，记录 RAM、上下文 token 和存储增长，验证任务结束后的引用释放及历史裁剪。这里是演示设计，不是已经完成的测试结论。

Q46：如何把这个系统做成可供前端调用的服务？

备考定位：A · 核心必答｜进阶。 答题抓手：API、持久化任务、worker 与取消语义。

参考答案：

可以用 FastAPI 等框架提供任务创建、状态查询、结果获取、审核和取消接口。接收请求时做身份校验和结构校验，创建持久化任务记录；需要长时间执行的操作提交给任务执行端，返回任务 ID，前端后续查询或订阅进度。

业务接口与模型适配、检索服务、工作流和设备执行分层，避免把全部逻辑写在一个 HTTP 路由中。请求使用明确的数据模型，错误区分输入非法、权限不足、容量限制和内部失败，客户端可以据此决定修正还是重试。

接口设计示例：

接口 作用 关键约束
POST /tasks 创建需求任务 校验请求，支持请求幂等；受理成功可返回 202 和任务 ID
GET /tasks/{id} 查询任务状态 校验任务归属，返回阶段与更新时间
GET /tasks/{id}/result 获取结果及产物引用 区分未完成、失败和已完成
GET /tasks/{id}/events 获取流式进度 支持事件序号和断线恢复策略
POST /tasks/{id}/reviews 提交 HIL 决定 审核权限、任务状态和方案版本校验
POST /tasks/{id}/cancel 请求取消 取消受理与外部设备真正停止要分开

常见追问： 用 FastAPI 的 BackgroundTasks 就能做长任务吗？

回答： 它适合轻量的进程内后台工作，不提供可靠队列和进程退出后的恢复保障。长实验应考虑持久化任务与独立 worker。

Q47：Python async/await、线程和进程怎么选？

备考定位：A · 核心必答｜进阶。 答题抓手：I/O 与 CPU 工作划分，以及取消的外部边界。

参考答案：

网络模型调用、数据库和消息等待主要是 I/O，可以使用真正的异步客户端，减少阻塞等待。async def 只是函数形式，内部调用同步阻塞 SDK 仍会阻塞事件循环；可以使用受控线程池隔离同步 I/O，或迁移到独立 worker。

纯 Python 的 CPU 密集工作在常见带 GIL 的 CPython 运行环境中通常适合多进程或外部计算服务；部分图像或数值库会释放 GIL，需要结合实现测试。外部编译器是子进程，应控制并发、超时、退出码和资源。

并发还需要连接池、信号量和背压。一次创建数千个协程并不等于服务能承担数千个模型请求，配额、内存和设备资源都有限制。

常见追问： 取消协程以后，设备操作也取消了吗？

回答： 不一定。任务取消只影响本地等待，外部服务和在线程中运行的阻塞函数可能仍在执行，必须跟踪任务状态并调用明确的取消或补偿接口。

Q48：数据库写任务和消息队列发任务，怎样保持一致？

备考定位：B · 重点追问｜难点。 答题抓手：outbox、重复投递与外部副作用一致性。

参考答案：

直接先写数据库再发消息，可能出现记录存在但消息没发出去；反过来也可能出现执行端收到任务但数据库没有记录。一个常见设计是在同一数据库事务里写任务和 outbox 事件，再由投递器把事件发送到消息队列。

发送端确认、消费者确认和业务执行成功是不同概念。投递和消费可能重复，消费者需要按任务或步骤标识去重，持久化状态后再确认；外部设备副作用仍通过幂等键和状态核对管理。

失败按类型有限重试，超过限制进入可追踪的失败或死信处理，不能无限重新入队。不要为了得到“本轮结果”清空共享接收队列，这会破坏其他任务的数据。

常见追问： 用了 outbox 是否就获得 exactly-once？

回答： 没有。它缩小了数据库与投递之间的一致性缺口，但重复投递和外部操作副作用仍需处理。这里是生产化设计建议，不能当作当前脚本已经实现的机制。

Q49：怎么给前端实时显示进度？SSE 与 WebSocket 如何选？

备考定位：B · 重点追问｜进阶。 答题抓手：事件流、断线恢复和首个有效进度。

参考答案：

如果主要是服务端向浏览器发送阶段、日志摘要或模型文本，SSE 通常比较简单；客户端提交需求、审核和取消仍可以走普通 HTTP。需要持续双向低延迟交互时，再考虑 WebSocket。

进度事件要包含任务 ID、事件序号、阶段、时间和可公开的内容。客户端断线后可根据事件序号补读，或者重新查询最新状态。浏览器断线不应默认取消后台硬件任务，事件重复时前端也要能够去重。

对于模型输出的工具参数或 JSON，流式片段不一定完整，不能收到一半就执行动作。完整解析、校验并得到必要授权后再调用工具。界面可以展示简短状态，不需要暴露内部思维链或原始敏感日志。

常见追问： 有 token 输出就说明整个任务响应快吗？

回答： 不代表。分别测首个有效事件、模型首 token、参数请求准备好和最终任务完成时间，避免用早期提示掩盖实际等待。

Q50：多人使用时如何保证数据和任务权限隔离？

备考定位：B · 重点追问｜难点。 答题抓手：对象级授权、检索权限与任务隔离。

参考答案：

身份认证确定请求者，授权决定他能查询哪些知识、使用哪些设备以及审核哪些任务。任务表、知识条目、图节点或关系、产物引用都要带必要的项目或租户范围，查询和执行阶段都检查权限。

检索时尽量在候选产生前限制授权范围，图扩展不能越过权限边界；进入模型前再确认上下文只包含允许的数据。缓存、日志、checkpoint 和下载链接也要考虑隔离，不能只保护 HTTP 页面。

数据库、图查询或工具执行不依赖模型自行遵守权限。审核人与提交人的权限是否分离、产物链接是否过期，按业务要求设计。

常见追问： 知道别人的 task_id 或 thread_id 能访问任务吗？

回答： 这些 ID 只是定位信息，每次请求仍必须做对象级授权检查；不能把难猜的 ID 当成权限机制。

Q51：哪些内容可以缓存？如何避免命中错误结果？

备考定位：B · 重点追问｜难点。 答题抓手：缓存键、知识版本、权限与失效条件。

参考答案：

参数定义、固定版本文档的 embedding 和符合条件的检索结果比较适合缓存。缓存键应覆盖知识版本、查询条件、权限范围、模型或检索配置。语义缓存还要防止两个近似表达在平台、目标或约束上实际不同。

设备操作和新实验结果不能因请求文字相同就直接跳过执行。有意重复采样属于新实验，不能误判为重试。LLM 输出缓存也可能保留过时解释，需要明确适用范围、有效期和失效策略。

Redis 可以用于缓存、速率限制或协调，但不能不加设计地当作全部任务事实的唯一存储。缓存击穿时可以合并同类请求或限制重建并发，失效更新要跟随知识与配置版本。

常见追问： 怎样测缓存收益？

回答： 分别报告冷缓存和热缓存的延迟、命中率与质量，验证命中没有跨用户或跨版本污染，而不是只报告最好的一次响应。

Q55：如果让模型同时看图片和 QCATS 报告，怎么设计？

Q56：如何部署、测试并发布一个 AI 应用版本？

Q57：AI 应用工程师需要掌握哪些模型推理基础？

备考定位：C · 按岗扩展｜进阶。 答题抓手：推理采样、上下文、延迟与部署基础。

参考答案：

需要理解 token、上下文窗口、生成阶段与资源成本。模型通常先处理输入上下文，也就是 prefill，再逐步生成 token，也就是 decode。长检索上下文会增加输入处理和缓存压力，长输出会增加生成时间，因此要区分首 token 延迟和完整响应延迟。

常见 Transformer 的注意力用于根据上下文形成表示；embedding 模型用于构建检索表示，reranker 比较查询与候选，生成模型负责理解或输出，这些角色不能互相混同。KV cache 缓存生成过程中已有 token 的键值以避免重复计算，不等于业务层答案缓存，也不能据此声称模型永久记住了用户。

如果岗位涉及自建推理服务，还需要比较模型精度、量化、显存、上下文长度、batch、并发与质量损失。连续批处理等机制可以改善利用率，但最终仍要测当前任务下的首 token、吞吐、尾延迟和正确率。只调用 QGenie 服务时，应说明底层部署由平台承担，并讲清自己负责的调用与监控边界。

常见追问： 模型上下文很大，为什么不能把整套参数库都放进去？

回答： 窗口容量不是质量保证。长输入增加成本和延迟，也可能分散注意、混入不适用知识；检索仍用于挑选当前决策需要的证据和适用范围。

参考答案：

先建立“用户需求—正确意图—相关参数集合”的标注集，保留参数来源与适用条件。评测参数是否召回完整、无关参数是否过多、描述是否对应正确字段，以及返回参数能否接入现有流程。相关集合可以包含必须召回项和可接受的替代项，不能假定所有需求只有唯一答案。

可以比较关键词检索、普通向量检索和图增强检索。在意图输入、候选数量和下游流程一致的条件下，检索层看 Recall@k、Precision@k、排序指标与关系完整性；交接层看参数标识有效率和接口接收成功率。若有模型输出参数列表，再检查是否存在未被检索证据支持的参数。对图扩展、社区信息、过滤或 rerank 做消融才能确定各自贡献；进一步改变参数分组或候选值后，要单独评测搜索策略收益。

还应区分“检索方式更好”和“知识中增加成功方案”的收益：在相同知识快照上比较检索算法，再单独比较是否提供历史成功方案，记录方案适用性、来源正确率和最终实验收益。测试运行新增结果隔离保存，不反馈进入同一轮静态对照。

要同时报告延迟和成本，并使用未参与调优的测试集。没有做过这些对比时，应说“为参数召回提供知识依据”，不直接宣称已量化降低幻觉。

常见追问： 检索正确但答案错误，属于哪里的问题？

回答重点： 区分入口实体未命中、关系遗漏、上下文组装丢失、模型误用证据和后续校验缺失，按链路定位。

Q30：如何评测整个 Agent，而不仅是 RAG？

备考定位：A · 核心必答｜进阶。 答题抓手：效果、效率、可靠性的分层评测。

参考答案：

我会把系统性能分为任务效果、运行效率和可靠性。效果看意图与参数召回是否正确，最终是否在预算内达到预先定义的目标；效率看前端响应、完整任务的 P50/P95 延迟、吞吐量与每个成功任务的成本；可靠性看超时、失败、重试、重复执行和人工干预。

具体做法是准备有标注的需求集，覆盖不同场景、口语表达、多目标、信息缺失和无答案输入。固定后端执行策略、设备条件和预算，对比规则检索、向量 RAG、GraphRAG，以及人工选参数。每个阶段打点记录时间、模型调用和执行结果；检索与社区证据改进、程序校验、候选搜索策略分别做消融；基线评测、各批候选及重试成本都记录，避免混淆收益来源。

测试同时包含离线标注集评测、使用工具替身的负载测试，以及受控实机任务。替身用于检验接口与调度，不代表真实业务耗时；实机失败和超时计入总体统计。详细指标口径、压测方式和口述模板见系统性能评测专项问答。

常见追问： LLM-as-a-judge 能做最终评分吗？

回答重点： 适合辅助评价解释质量等主观项，但需与人工标注校准；配置合法性、执行事实和客观指标应使用确定性检查。

Q31：出问题如何排查？模型升级如何回归？

备考定位：A · 核心必答｜进阶。 答题抓手：跨节点 trace、故障定位与版本回归。

参考答案：

为一次任务建立统一 trace，串联图节点、模型版本、提示词版本、检索结果、工具调用、配置版本、任务 ID 和评测产物，同时记录各阶段耗时、token、错误及重试。

定位时先看事实链：输入是否完整、检索是否适用、模型动作是否合法、工具是否实际执行、结果是否属于当前任务，再看最终解释。无需依赖不可观察的内部思维链。

模型、prompt、检索或工具 schema 更新后，在固定回归任务集上比较成功率、关键错误类型、延迟和成本。通过后分阶段发布，并保留回滚版本。

常见追问： 为什么同样输入仍可能得到不同结果？

回答重点： 模型采样、服务实现、检索索引和外部设备状态都可能变化；记录版本和条件能提高可追溯性，但不能轻易承诺绝对复现。

Q32：怎么降低成本和延迟？项目难点怎么讲？

备考定位：B · 重点追问｜进阶。 答题抓手：按实测瓶颈优化，并用真实故障讲项目难点。

参考答案：

先测量耗时分布，区分模型、检索、硬件实验和等待时间。减少不必要的模型调用，把等待轮询、参数校验和固定格式处理交给程序；压缩上下文，对稳定定义做版本化缓存，并在无依赖时并行执行。

缓存要考虑权限和知识版本，动态实验结果不能错误复用。更换小模型或减少检索内容后，还要重新验证任务成功率，不能只看费用下降。

讲个人难点时选一个真实案例，按“具体故障—如何定位—方案取舍—验证结果—剩余限制”展开。例如回包错配、参数版本混淆或图检索关系不完整。没有解决过的问题不要编造成经历。

常见追问： 如果硬件采集占绝大部分时间，优化 prompt 长度有什么意义？

回答重点： 先优化主要瓶颈；模型优化也可能降低费用，但不能把它夸大成端到端提速的主要原因。

P01：面试官问“你怎么评测整个系统的性能”，怎么完整回答？

备考定位：A · 核心必答｜进阶。 答题抓手：两分钟讲清分层指标、对照和测试环境。

两分钟口述答案：

我从任务效果、运行效率和可靠性三个方面评测，不能只看模型回答是否通顺。

首先建立有人工标注的需求集，包含用户场景、正确意图、相关参数及适用条件。意图层检查目标与约束提取，RAG 层检查参数 Recall@k、Precision@k 和不适用参数比例，接口层检查召回参数能否正确映射到配置。端到端成功定义为：任务按需求执行，并在固定预算内达到预先设定的验收目标，有可追溯的配置和评测记录。执行完成和画质达标分别统计。

其次，我会测前端和全流程两种延迟。前端从用户提交到首批可执行候选准备好，其中需要记录初始 QCAT 评测；全流程还包括排队、配置编译、各候选实验和整批反馈迭代。记录各阶段耗时，报告 P50、P95、吞吐量和资源利用率。硬件占用比较长时，先定位实际瓶颈，不能把模型响应时间当成整个系统耗时。

第三，测试模型超时、编译失败、设备断连和回包异常，统计失败率、恢复率、重复执行及人工干预，并记录模型 token、编译资源和设备占用，计算每个成功任务的平均成本。

为了证明改进有效，固定后端策略、设备条件和实验预算，对比规则或普通向量检索与 GraphRAG；社区证据、程序校验和分组细化的收益另做对照。最终报告同时包含成功率、耗时、成本和失败类型，避免只展示成功案例。

P02：这些指标怎么计算？“成功率”分母是什么？

备考定位：A · 核心必答｜难点。 答题抓手：成功率分母、目标达成与执行完成的区别。

参考答案：

先规定任务单位和统计范围。一次用户需求算一个任务；其中多次候选配置测试算实验，不把它们混入任务成功率分母。任务集合在实验开始前固定，失败和超时仍留在分母中，不能统计到一半排除。

指标 计算口径 用途
意图槽位 Precision/Recall/F1 对照标注的场景、目标、约束分别计数，再报告汇总 发现漏约束、误解目标
严格意图正确率 所有必要字段正确的需求数 / 已标注需求数 衡量完整理解能力
参数 Recall@k 前 k 个候选中相关参数数 / 标注相关参数总数 检查漏召回
参数 Precision@k 前 k 个候选中相关参数数 / 前 k 个实际返回候选数 检查无关参数占比
参数适用性错误率 平台、版本或模块不适用的候选数 / 返回候选数 发现语义相近但不可用的参数
接口接收成功率 下游成功解析并接收的合法请求数 / 实际提交请求数 衡量衔接，不等同于执行成功
执行完成率 产出有效执行结果的任务数 / 受支持任务总数 反映工程可用性
目标达成率 在预算内经独立规则确认达标的任务数 / 受支持任务总数 反映业务效果，失败与超时计入分母
全自动达成率 无额外人工介入且达标的任务数 / 受支持任务总数 检验自主程度
人工干预率 需要额外人工处理的任务数 / 受支持任务总数 衡量人工工作量
单任务实验数 一个任务实际执行的配置候选数 衡量搜索成本与效率

计算细节： 不同工具对 Precision@k 的分母可能固定为 k；这里采用实际返回数，需同时报告返回数量和空召回率，不能通过只返回一个候选获得看似很高的精度。无相关答案的样本不计算普通 Recall，单独测正确拒答或补充信息的比例。相关参数可有多组合理答案，需要专家标注可接受集合与必需项。

多意图指标建议同时报告宏平均和各场景结果，避免高频简单任务掩盖困难场景。零个成功任务时，每成功任务成本不可计算，明确报告无成功任务及总消耗，不填零。

常见追问： 用户请求根本不支持，正确拒绝算失败吗？

回答： 不与支持任务混算画质达成率。预先分层统计：支持任务看执行和目标达成；不支持、缺信息等任务看路由、澄清或拒答是否正确。同时报告全体输入上的处理正确率及各类样本数量，不能事后移除失败任务。

回答： 样本太少时尾部估计不稳定。报告样本数、具体范围和不确定性，积累更多任务后再比较稳定分位数，不用少量样本给出精确性能承诺。

P04：怎么做并发和吞吐量测试？硬件不够怎么办？

备考定位：B · 重点追问｜难点。 答题抓手：硬件容量、负载模型和队列背压。

参考答案：

分两层测。第一层用工具替身隔离硬件，施加可控执行时间和错误，逐级增加请求到达率或并发数，观察前端吞吐、P95、队列积压、模型限流和错误率。测试要说明采用固定并发还是固定到达率、运行时长及预热方式。

第二层用真实设备执行受控任务，测每小时完成任务数、每台设备的候选实验数、设备占用、排队时间和实际错误。不同任务轮数差异很大，所以还要报告每任务实验数分布，避免“任务数”隐藏工作量变化。

受理吞吐、完成吞吐和成功完成吞吐分别统计。压力下只有受理量增加、队列持续增长，说明不能稳定承载该流量。并行编译可能提速，但设备独占或评测端也可能成为瓶颈。

原代码的接收队列处理尚不能证明多任务并发安全；正式并发实机前，应先完善结果关联与队列隔离，避免清队列导致其他任务回包丢失。当前只能报告实际验证过的单任务或受控运行能力。

常见追问： 多加 Agent 就能提高吞吐吗？

回答： 不能。如果瓶颈是设备占用或模型配额，多开决策循环只会增加排队和成本。应根据瓶颈增加对应资源或调整调度。

P05：评测数据集和对照实验怎么设计？

备考定位：A · 核心必答｜难点。 答题抓手：数据切分、基线、消融和实机条件控制。

参考答案：

从真实需求中脱敏采样，再补充同义表达、多个目标、约束冲突、信息缺失、无对应参数和平台不匹配等边界样本。由领域人员标注意图、相关参数、适用条件、预期路由和验收规则，争议样本复核后保留标注依据。

数据按任务或方案家族划分开发集和冻结测试集，避免同一需求改写后分别进入两边。调参和提示词优化只用开发集；测试时固定知识库、模型、提示词、工具和评测版本。知识库本来就包含参数文档是正常设置，但不能把测试题答案或测试运行结果泄露进检索内容。

常见追问： 能不能同时换模型、加图检索、改细扫，再说提升来自 GraphRAG？

回答： 不能。组合改进可以报告整体结果，单组件收益要通过固定其他条件的对照或消融确认。

P06：系统可靠性怎么测？

备考定位：B · 重点追问｜难点。 答题抓手：故障注入、预期状态与重复副作用检查。

参考答案：

在受控测试环境注入故障，检查实际状态变化、恢复行为和副作用，而不只检查有没有抛异常。

故障场景 预期行为 验证证据
意图输出缺字段、RAG 空召回 有界修正、澄清或结束，不编造参数进入执行 路由状态与下游零提交记录
XML 映射失败或编译失败 停止该候选，明确失败阶段 配置差异、编译日志、未部署记录
模型超时或限流 有界退避重试或返回失败 调用次数、等待时间、费用

统计各类故障发生数、正确处理率、恢复率、恢复耗时和人工干预，注明哪些机制已实现。没有 checkpoint 或幂等机制时，测试结论可以是“当前不支持自动恢复”，不能用模拟成功路径代替故障验证。

常见追问： 什么叫可靠性测试通过？

回答： 预期状态、数据完整性和副作用都符合规则。例如超时能够结束还不够，还必须检查是否多执行一次、是否错用了其他候选结果。

P07：怎么统计成本，如何决定先优化哪里？

备考定位：B · 重点追问｜进阶。 答题抓手：token、设备占用与每成功任务成本。

参考答案：

分开记录意图识别、检索与各轮模型推荐调用，包括输入输出 token、重试和实际使用的 embedding / rerank；再记录初始评测、每批候选数、编译资源、存储及设备占用分钟数。对知识积累另计文档解析/OCR、实体关系抽取、embedding、索引与社区更新成本；已有成功方案仍需本次验证，不能把历史评测当作免费完成新实验。有内部计费单价时换算费用，没有单价时报告资源单位，不虚构金额。

优化前先看成本与延迟分布。模型成本高时减少不必要上下文与重试；设备时间占主导时，更准确的召回和更有效的候选选择可能减少实验次数。缓存参数定义要绑定知识版本，不能缓存动态实验结果后误当成新测试。

最终同时比较目标达成率、总成本、每任务成本和每成功任务成本。一个方案少调几次模型但让更多任务失败，可能使每成功任务成本反而更高。

常见追问： 召回更多参数能提高 Recall，为什么不全部返回？

回答： 候选越多可能增加无关配置和实验成本。要在固定验收目标下比较覆盖率、Precision、实验次数和达成率，选择合理的候选规模。

八、Harness Engineering 驾驭工程

从运行环境定义，过渡到项目实践、固定模型的对照验证、经验沉淀和个人交付能力。

这里按 AI Agent 语境中的 Harness Engineering 理解“驾驭工程”：围绕模型搭建能执行、能观察、能验证并约束行为的运行环境。它没有一套唯一固定的组件清单。若面试官指的是特定公司的框架或测试 harness，应先对齐范围。

本章题目： Q58、Q59、Q60、Q61、Q62、Q63。

Q58：什么是 Harness Engineering？和写提示词有什么区别？

备考定位：B · 重点追问｜基础。 答题抓手：工具、上下文、约束和验证组成的运行环境。

参考答案：

我理解的 Harness Engineering，是把模型放进一个能持续完成任务的工程环境：明确任务和验收条件，提供合适的上下文与工具，管理执行状态、权限和预算，再用真实反馈验证结果、处理失败。

提示词是其中一个部分。即使模型理解了目标，如果拿不到正确文件、工具返回不可读、执行环境不一致或没有验证反馈，也可能无法完成任务。因此改进 Agent 时，既看模型能力，也看模型周围的工作系统是否支持它正确行动。

概念 主要关注 本项目中的例子
Prompt Engineering 如何表达当前任务和输出要求 提取场景、目标与约束的提示词
Context Engineering 当前步骤需要哪些信息、如何组织和加载 参数描述、来源、实验历史摘要
Harness Engineering 模型怎样在环境中执行、验证并受控推进 LangGraph 状态、检索工具、配置校验、设备接口、HIL、评测与恢复

三者有交集，不能把 Harness 简单等同于更长的系统提示词，也不能认为引入某个框架就自动完成了驾驭工程。

常见追问： 和测试 harness 有什么关系？

回答： 传统测试 harness 组织测试环境、输入与执行结果；Agent harness 的范围通常还包含上下文、工具和任务生命周期。测试验证是其中关键部分，具体术语范围仍以讨论场景为准。

Q59：你的 Camera Agent 项目有哪些 Harness Engineering 实践？

备考定位：B · 重点追问｜进阶。 答题抓手：把项目机制映射到 Harness，并区分现状和设计。

参考答案：

可以沿完整链路解释：前端用结构化意图减少歧义，用 RAG 提供参数证据；后端把参数映射到实际配置，调用编译与实验工具，并把 QCATS 反馈交回迭代过程。LangGraph 表达状态与流转，这些构成模型开展工作的环境。

如果进一步完善，我会加入独立校验、任务身份关联、预算限制、HIL 审核、幂等执行和恢复机制，并明确每一步的输入输出与完成条件。哪些已经实现就用实际代码和轨迹证明，哪些仍是原脚本的不足就列为改进项。

核心是让模型的建议经过真实执行和可检查的反馈，而不是只要求它“认真分析”。例如召回参数后校验字段身份，执行后核对配置和结果归属，停止时分别报告流程状态与目标达成状态。

常见追问： 最能体现驾驭工程价值的一次改进是什么？

回答： 挑一个真实问题，例如错误参数映射、反馈错配或重复执行，解释你改变了哪项环境约束或反馈机制，以及相同模型下错误率如何变化。没有做过对照时，不编造提升数据。

Q60：同一个模型换了 Harness，为什么表现会差很多？怎么证明？

备考定位：B · 重点追问｜进阶。 答题抓手：固定模型，比较运行环境改动的质量与成本。

参考答案：

模型的实际表现取决于它能看到的信息、可执行的动作，以及是否及时得到正确反馈。例如检索结果没有版本信息、工具错误只返回“失败”，会使模型难以纠正；提供准确字段、错误分类和可重试条件，可能让同一个模型更有效地推进任务。

验证时固定模型、任务集、预算和外部条件，分别改变上下文组织、工具接口或验证反馈，比较任务成功率、无效调用、人工接管和总成本。一次修改多个部分时，只能先报告整体效果，不能把全部收益归到一个组件。

还要避免把测试答案写进提示词、让验证器只检查模型偏好的结果，或者增加预算后宣称架构更有效。模型能力仍有上限，好的 Harness 能改善信息和执行条件，但不能保证所有任务可解。

常见追问： 提高成功率但调用次数翻倍，算改进吗？

回答： 要看业务目标和成本约束，同时报告质量、延迟、费用及每成功任务成本，比较是否值得，而不是只选一个有利指标。

Q61：如果用 Agent 写代码，怎样设计仓库和开发环境？

备考定位：C · 按岗扩展｜进阶。 答题抓手：仓库入口、可复现环境和可验证任务边界。

参考答案：

让 Agent 容易找到入口、运行项目并验证修改。提供简洁的项目说明、目录职责、依赖安装方式、构建与测试命令，以及必须遵守的接口边界；具体模块文档按需加载，避免把全部知识塞进一个超长文件。

对格式、类型、接口和依赖方向等可以机器检查的规则，放进 formatter、lint、类型检查或测试中。工具错误要明确到失败原因与相关位置，给 Agent 可用反馈；文件修改通过 diff 审查，重要行为用验收测试或独立评估验证。

执行环境应可复现，必要时用隔离工作目录或容器限制影响范围。仓库说明是指导，不能替代运行时权限。模型说“测试通过”时，要检查真实命令、退出码和结果，并确认没有删掉或弱化测试来通过检查。

常见追问： Agent 修复失败后，你会不断追加提示词吗？

回答： 先定位是目标不清、上下文缺失、环境错误还是代码缺陷，改进相应环节。反复补文字而不修复工具或环境，会让提示词越来越复杂但问题仍在。

Q62：怎样把一次成功经验沉淀成可复用能力？

备考定位：B · 重点追问｜进阶。 答题抓手：将经验沉淀为有触发条件、步骤和验证的 Skill。

参考答案：

可以把稳定过程整理成 Skill 或运行手册，写清触发条件、输入要求、步骤、工具接口、验证方式、失败处理和适用边界。确定性且重复的步骤可以抽成脚本，领域事实保存在有来源的知识库，不能只保存一段成功聊天记录。

经验要先经过复查和新任务验证，再推广使用。避免保存凭据、偶然的路径、某台设备的临时状态，或把一次成功的参数值当成普适规则。新版本保留变更和回滚方式，失效经验可以撤销。

在这个项目里，自动调参成功结果已经会持久化，但保存配置方案不等于自动生成 Skill。参数事实和已有方案适合进入 RAG/GraphRAG，如何查询、校验、提交和处理结果的流程经验可以进入 Skill；两类内容关联使用，但职责不同。

常见追问： Skill 写得越多，Agent 就越强吗？

回答： 不一定。重复、冲突或触发范围过宽会增加干扰，需要维护检索或加载规则、验证样例和版本，衡量实际复用收益。

Q63：如何评价自己“驾驭 Agent”的能力，而不是只说会用工具？

备考定位：B · 重点追问｜进阶。 答题抓手：用实际交付、失败定位和纠正成本说明能力。

参考答案：

我会展示一个可复查的任务链：如何明确目标和约束，准备上下文与工具，观察执行结果，定位失败，调整环境或流程，并独立验证最终产物。说明哪些工作由 Agent 完成，哪些判断和修复由我完成。

指标可以包括在固定任务集上的完成率、人工活跃处理时间、纠正次数、无效工具调用、总耗时和成本。还要展示失败案例，解释模型建议为何被拒绝、什么时候切换方法或交给人工。

“输入一句话就生成了代码”只能证明工具使用，不足以证明工程能力。能复现问题、设计边界、验证结果并把经验转成可维护流程，才是更有说服力的证据。

常见追问： 是不是人工越少越好？

回答： 要结合任务风险和验收标准。有些环节需要人的业务判断，目标是减少不必要的重复劳动，并让关键决策有证据，而不是单纯追求零接管。

Q66：Hermes 的 Skills、记忆和 RAG 有什么区别？

Q67：Hermes 宣称会持续学习，是否意味着它在训练模型？

参考答案：

训练或微调需要单独的数据、训练过程和模型版本证据。一个 Agent 更了解用户或能复用流程，可能只是拿到了更合适的上下文，而不是底层模型参数改变。

参考答案：

官方 README 描述了本地、容器和远程等工具执行后端，以及定时任务和消息入口。使用时首先确认当前工具在哪里运行、能访问哪些文件和网络、采用什么凭据、出了问题如何停止和核查。

容器或远程后端不自动等于安全隔离，挂载目录、网络访问和授权工具决定实际边界。定时任务还需要明确时区、任务重叠、重复执行、失败通知和成本限制；这些是需要核验的使用条件，不能假设软件替用户全部处理。

在个人使用经验中，只讲实际启用的后端与入口。如果是本地终端使用，就不声称已做多平台消息接入或生产级调度。

常见追问： 为什么这也属于 Harness Engineering？

回答： 因为执行后端、文件可见性、工具范围、反馈和预算直接影响 Agent 能否正确完成任务，属于模型周围的工作环境设计。

Q69：如果将 Hermes 的经验引入 Camera Agent，你会怎么做？

备考定位：C · 按岗扩展｜进阶。 答题抓手：将通用经验适配到受控业务链路。

参考答案：

先借鉴能力组织方式：将稳定流程沉淀成可审查的 Skill，按需加载上下文，把任务执行与模型建议分开，并保留实际轨迹用于验证。参数事实仍从领域 RAG 召回，硬件操作仍通过现有受控接口执行。

如果确实需要让 Hermes 成为入口，可以封装“查询参数、提交受约束任务、查询状态、获取报告”等工具。参数映射、权限、HIL、设备独占与验收规则保留在业务服务侧，不能用通用终端权限替代这些约束。整个集成属于设计方案，尚未确认已经接入。

我会在固定任务上比较直接使用原入口与新增 Agent 入口后的成功率、调用成本、人工干预和错误类型。只有带来可测的使用或工程收益，才值得增加这一层。

常见追问： 用过 Hermes 和理解 Agent 架构之间差在哪里？

回答： 用过说明能完成配置与任务；理解架构还需要解释状态、上下文、工具执行和验证边界，能定位失败并判断哪些能力该复用、哪些应留在业务系统中。
