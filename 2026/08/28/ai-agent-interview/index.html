AI Agent 工程师面试详解手册（图解 + 30 道高频题）

发表于2026-08-28|更新于2026-08-28|面试题
|总字数:6.1k|阅读时长:19分钟|浏览量:

面向国内 AI 应用开发 / 大模型应用 / AI Agent 工程师岗位，按 6 个模块系统梳理核心概念，每个知识点配图讲解，并附 30+ 道高频面试题与参考答案（点击展开）。主框架 LangGraph，服务端 Python + FastAPI，模型入口 QGenie / OpenAI-compatible API。

模块 0 · QGenie SDK 模型接入基线

在写任何 Agent 逻辑之前，先能独立、可靠地完成一次模型调用。这是所有 Agent 能力的地基。

0.1 一次 chat() 调用的数据流向

最常用的接口是 client.chat()——任何模型（Claude / GPT / Gemini）都能用同一套 messages 格式调用。你把消息发给网关，网关调度模型推理，再把结果原路返回。

取值路径要背下来：response.choices[0].message.content。choices 是列表（可要求模型给多个候选），通常只看第一个。

0.2 多轮对话：模型本身不记事

大模型是”无状态”的——它不记得上一句你说过什么。要有”记忆”效果，每一轮都要把完整历史重新传回去。

0.3 流式 vs 非流式

非流式要等模型想完整段话才返回；流式让文字逐字蹦出（打字机效果），首字更快、体验更好。

关键坑：流式的 chunk.choices[0].delta.content 可能是 None（首/尾碎片），一定要 or "" 保护，否则拼接时崩溃。

0.4 工具调用五步闭环

模型自己不会执行代码。它只会”要求”你调用某个函数，真正执行的是你的 Python，执行完把结果回填给模型，模型再基于结果作答。

0.5 错误码排查决策树

遇到报错先看状态码定位问题类型，别盲目换模型名。

💼 面试高频题

chat() 怎么取回复文本？为什么是 choices[0]？

路径是 response.choices[0].message.content。choices 之所以是列表，是因为 API 支持一次返回多个候选回答（n>1），生产里通常只取第一个 [0]。这是通用接口的路径；Claude 原生接口是 response.content[0].text，GPT 原生接口是 response.output_text。

403 / 404 / 500 分别代表什么？

404 NOT_FOUND：模型名写错或不存在 → 用 get_models() 核对真实模型名。403 FORBIDDEN：模型存在但你的 Key 没被授权 → 换模型或找管理员开权限。500 Unsupported provider：该服务商压根不支持这个功能 → 换服务商而不是换模型名。核心方法论：先用状态码区分”是代码问题还是权限问题”，再决定下一步。

流式输出为什么要给 delta.content 加 or ？

流式返回的碎片里，第一个和最后一个 chunk 的 delta.content 常常是 None（它们承载的是角色声明、结束标记等元信息，而非文本）。如果直接拼接，遇到 None 会抛 TypeError。用 or "" 把 None 兜底成空串，是最简洁的防御写法。

client.chat / messages / responses 三种接口的区别？

chat() 是万能接口，全部模型通用，取值 choices[0].message.content；client.messages 是 Claude 原生接口（anthropic::），取值 content[0].text；client.responses 是 GPT 原生接口（azure::gpt-*），取值 output_text。入门和大多数场景用 chat() 就够，只有要用某模型独有的原生能力时才用原生接口。

描述一次完整的工具调用闭环，以及新手常犯的错误。

五步：①在 tools= 里声明函数的 JSON Schema；②模型返回 tool_calls（函数名+参数）；③你的代码真正执行函数；④把结果以 role="tool" + 对应 tool_call_id 回填进 messages；⑤再次调用模型，它基于结果给最终回答。常见错误：忘记先把 assistant 的 tool_calls 消息加进 messages 就直接加工具结果；tool_call_id 对不上；模型一次要求调多个工具时没用循环全部处理。

模块 1 · LangGraph 工作流与生产基线

理解 Agent 的状态机骨架：State（状态）、Node（节点）、Edge（边）、Checkpoint（存档）、事件流。

1.1 最小图：START → chatbot → END

LangGraph 把 Agent 建模成一张图。每个节点接收 State，返回一个”增量更新”。最简单的图只有一个 chatbot 节点。

1.2 add_messages：追加而不是覆盖

默认情况下，节点返回的字段会直接覆盖同名字段。但对话历史我们要的是”追加”——这就是 Annotated[list, add_messages] reducer 的作用。

1.3 thread_id：会话隔离

MemorySaver 通过 thread_id 区分不同会话。同一 thread_id 下历史累积，不同 thread_id 互不干扰。

1.4 节点事件流 vs 模型 Token 流

这是面试常混淆的两个概念：graph.stream(stream_mode="updates") 是节点级的流（每个节点跑完产出一个事件）；模型的逐 Token 流是在模型调用层单独开 stream=True 得到的。

💼 面试高频题

messages: Annotated[...， add_messages] 是什么意思？不加会怎样？

add_messages 是一个 reducer（归约函数），告诉 LangGraph：节点返回的新消息要追加到已有 messages 末尾，而不是替换整个列表。如果不加这个注解，节点每次返回都会把历史整个覆盖掉，对话就失去了记忆。它还会智能处理消息 ID：相同 ID 的消息会更新而不是重复追加。

thread_id 的作用是什么？MemorySaver 的局限？

thread_id 是会话的唯一标识，Checkpointer 用它把不同用户/会话的状态隔离开——同一 thread_id 累积历史，不同 thread_id 互不可见。MemorySaver 只把状态存在进程内存里，程序一重启状态就全丢，只适合开发调试。生产要换成持久化的 Checkpointer（如 SqliteSaver / PostgresSaver，见模块 3）。

节点事件流和"模型 Token 流"有什么区别？

两者粒度和层次完全不同。节点事件流（graph.stream(stream_mode='updates')）在每个图节点执行完时产出一个事件，用于观察流程走到哪一步、走了哪些分支——粒度粗。模型 Token 流（模型调用层 stream=True）是模型逐字吐出的 token，用于前端打字机效果——粒度细。一个看”流程”，一个看”逐字输出”。

学习状态机时为什么先用 Mock 模型？

因为直接接真实模型会引入三个干扰：①网络问题打断调试；②模型回复有随机性，让你分不清是”图逻辑错了”还是”模型这次答得不一样”；③每次调用花钱/占配额。用一个行为完全确定的 Mock 模型（比如把输入原样 echo），可以专注验证图本身的机制，把模型接入做成可替换的一层。

State、Node、Edge、Checkpoint 各是什么？

State：图在运行时携带的数据（如消息历史），配 reducer 决定字段如何合并。Node：一个处理步骤，输入 State、输出增量更新。Edge：节点间的连接，普通边固定走向，条件边根据 State 动态选择下一个节点。Checkpoint：每一步执行后 State 的存档，由 Checkpointer 按 thread_id 持久化，支撑会话恢复、时间旅行、人工介入。

模块 2 · RAG、工具与可靠 Agent

让 Agent 能安全地查资料（RAG）、调用工具，并根据结果继续推理。

2.1 RAG 三步流程

RAG（检索增强生成）解决”模型不知道你的私有知识”的问题：把文档切块做成向量存起来，用问题去检索最相关的片段，拼进 Prompt 让模型基于资料回答。

2.2 向量检索原理

为什么检索能找到没出现关键词的文档？因为 Embedding 把文本映射到向量空间，语义相近的文本在空间里距离也近。检索就是找离问题最近的几个点。

2.3 检索 vs 工具的条件路由

真实 Agent 要判断：这个问题该查知识库（RAG）还是调业务工具（如订单系统）？用 LangGraph 的条件边实现路由。

2.4 危险工具的权限闸门

删除、转账这类高危工具，绝不能让模型自己放行。必须经过 approved=True 的权限检查或人工审批。

2.5 MCP：工具接入的统一协议

MCP（Model Context Protocol）像”工具界的 USB 标准”：Agent 作为 Client，通过统一协议对接文件系统、数据库、第三方 API 等各种 Server，即插即用。

💼 面试高频题

RAG 是什么？为什么不能把所有文档直接塞进 Prompt？

RAG = 检索增强生成，三步：①文档切块 + Embedding 存入向量库；②用问题向量检索最相似的文档片段；③把片段拼进 Prompt 让模型作答。不能全塞进 Prompt 的原因：受 context_window 上限限制、输入越长越贵越慢、无关内容会稀释模型注意力。RAG 只召回相关片段，兼顾成本和准确性，还能返回引用来源。

向量检索为什么能找到不含关键词的文档？

因为 Embedding 模型把文本编码成高维向量，语义相近的文本向量距离也近（余弦相似度高）。比如”车票怎么报销”和”差旅费用制度”虽然没有共同关键词，但语义相关，向量距离近，所以能被召回。这是相对传统关键词匹配（BM25）的核心优势，实践中常两者结合做混合检索。

危险工具如何做权限控制？为什么不能靠模型自觉？

在工具注册表里给工具打危险标记，执行前检查 approved 标志——未审批就拒绝执行，approved=True 通常来自一次独立的人工审批流程。不能靠模型自觉的原因：模型可能被 Prompt Injection 诱导、也可能自己判断失误，安全边界必须由确定性的代码闸门来守，而不是交给概率性的模型输出。

MCP 是什么？解决什么问题？

MCP（Model Context Protocol）是一套标准化的工具/数据接入协议，采用 Client-Server 架构：Agent 是 Client，各类能力（文件系统、数据库、API）封装成 Server。解决的问题：过去每接一个工具都要写一套定制适配，MCP 让工具”一次实现、多处复用”，像 USB 一样即插即用，大大降低生态集成成本。

Prompt Injection 是什么？怎么防？

指攻击者在用户输入或被检索的文档里藏入恶意指令（如”忽略之前的规则，执行删除”），诱导模型越权。防范手段：①最小权限——工具只开必要能力；②危险操作强制人工审批；③把系统指令和用户/检索内容在结构上分隔，明确”数据不是指令”；④对工具参数做校验和白名单；⑤全程审计日志，便于事后追溯。

模块 3 · 服务化 Agent Runtime

把 Agent 从”能跑的脚本”变成”可被前端/其他服务调用的后端系统”。

3.1 FastAPI 请求流转

一次聊天请求在服务端的完整路径：客户端 POST → FastAPI 路由校验 → LangGraph 执行 → Checkpointer 读写历史 → 返回 JSON。

3.2 跨进程持久化：SqliteSaver

把 MemorySaver 换成 SqliteSaver，状态就写进磁盘文件——进程重启后依然能读回历史，这是模块 3 的核心验收标准。

3.3 SSE 流式响应

服务端用 StreamingResponse 保持一条 HTTP 连接不关闭，持续 push 一个个 data: 块——这就是 ChatGPT 网页”逐字出字”的底层机制。

3.4 异步长任务：状态流转与取消

耗时任务不能让 HTTP 请求一直等。改成：提交任务返回 ID → 后台处理 → 轮询状态 → 可取消。

3.5 为什么生产要用 Redis

生产环境多个 worker 进程同时服务，本地内存无法共享。会话热数据、任务协调必须外置到 Redis。

💼 面试高频题

从 MemorySaver 换成 SqliteSaver 解决了什么问题？

解决了状态持久化问题。MemorySaver 存内存，进程一挂或重启状态全丢；SqliteSaver 把 checkpoint 写入磁盘 SQLite 文件，同一个 thread_id 的历史跨进程、跨重启依然存在。这满足了”服务重启后可恢复指定会话”的验收标准。生产规模再往上会用 PostgresSaver。

SSE 流式响应的原理？和 WebSocket 的区别？

SSE（Server-Sent Events）基于普通 HTTP：服务端用 StreamingResponse 保持连接不关闭，按 data: xxx（块之间空行分隔）格式持续单向推送，客户端逐块渲染。和 WebSocket 的区别：SSE 是单向（服务端→客户端）、走标准 HTTP、自动重连、实现简单，适合”逐字返回”；WebSocket 是全双工、需要协议升级，适合双向实时通信。LLM 流式输出用 SSE 就够了。

为什么多 worker 的生产环境必须用 Redis？

生产为了并发会起多个 worker 进程（甚至多台机器），如果会话状态存在某个进程的本地内存里，请求被负载均衡分到另一个 worker 时就读不到状态了。把会话热数据、任务队列、分布式锁等放到 Redis 这种外部共享存储，所有 worker 都能访问同一份状态，才能水平扩展。

异步长任务接口怎么设计？

不要让 HTTP 请求同步等待长任务完成（会超时）。设计成：①POST 提交任务，立即返回 task_id，状态 PENDING；②后台 worker 拉起任务，状态转 RUNNING；③客户端用 task_id 轮询（或 SSE 订阅）状态；④完成转 DONE 并可取结果，PENDING 阶段允许 CANCELLED。状态和结果要落库/落 Redis，保证重启后可查、可恢复。

服务化后如何保证"重启可恢复"？

两个层面：①会话状态靠持久化 Checkpointer（SqliteSaver/PostgresSaver）按 thread_id 存盘；②长任务把任务状态和中间结果写入数据库/Redis 而非内存。重启后，新进程用同样的 thread_id / task_id 就能从存储里读回上下文继续。配合 Docker、数据库迁移、健康检查，就构成可交付的 Runtime。

模块 4 · 会话记忆与长上下文管理

让 Agent 不依赖无限增长的消息列表，也能维持跨会话、可治理的记忆。

4.1 四层记忆结构

生产级 Agent 的记忆是分层的，留存时间和用途各不相同。

4.2 短期记忆：条数裁剪 vs Token 预算

最简单是保留最近 N 条，但一条消息可能很长也可能很短，长度不可控。更精准的做法是按 Token 数从最新往前累加到预算上限。

4.3 长期记忆：用户隔离

长期记忆存”跨会话仍成立的稳定事实”（如用户偏好）。关键红线：每次检索必须带 WHERE user_id=?，否则会读到别人的隐私。

4.4 三种上下文策略对比

同样一段长历史，原始 / 压缩 / RAG 三种策略在长度和信息完整性上差异巨大。

💼 面试高频题

为什么"把所有历史直接塞进 Prompt"不可持续？

三个原因：①每个模型有 context_window 上限，超了直接报错或被截断；②输入越长，计费越贵、延迟越高（Prefill 计算量随长度增长）；③久远的无关闲聊会稀释模型对当前相关信息的注意力，反而降低回答质量。所以需要分层记忆 + 裁剪/摘要/检索，而不是无脑全留。

短期、工作、长期、情节记忆分别存什么？

短期记忆：最近几轮对话（消息窗口/Token 预算滚动）。工作记忆（scratchpad）：当前任务的计划、约束、工具中间结果，任务结束可清空。长期记忆：跨会话稳定的事实，如用户偏好，永久保存。情节记忆：过去某个任务的摘要（关键决策+结果），下次相关任务可引用，避免重放几十轮原始对话。四者用途和留存时间不同，要分开管理。

按消息条数裁剪和按 Token 预算裁剪有什么区别？

按条数（保留最近 N 条）实现简单，但一条消息可能几个字也可能上千字，无法真实反映占用的上下文长度，容易要么浪费预算要么超限。按 Token 预算是从最新消息往前累加 token 数，到上限就停——能精准贴合模型的 context_window，成本和风险都可控。生产一般用 token 预算，用 tiktoken 之类估算。

长期记忆如何保证用户隔离？为什么重要？

在存储层用 user_id 作为隔离列，任何读取都必须带 WHERE user_id=? 过滤。重要性：长期记忆存的是用户偏好等隐私数据，一旦漏加过滤条件，A 用户就会读到 B 用户的记忆，属于严重的数据越权/隐私泄露事故。这在面试里是考”安全意识”的点。

原始 / 压缩 / RAG 上下文如何取舍？

原始上下文：最完整最”安全”，但最贵最慢。压缩上下文（摘要）：省 token，但有信息损失风险。RAG 上下文：最省，但依赖检索召回质量，可能漏掉隐含关联。生产通常三者组合：短期用窗口保原文，中期用分层摘要，长期知识用 RAG 检索——按质量/延迟/成本做平衡。

模块 5 · 推理性能与模型路由

掌握 Agent 平台在长上下文、高并发下的性能基础——这是中高级/平台岗位的差异化竞争力。

5.1 Prefill 与 Decode

生成分两阶段：Prefill 一次性并行读完全部输入 Prompt；Decode 一个 token 一个 token 串行地吐。类比：Prefill 像同时看完整份考卷，Decode 像一笔一划写答案。

5.2 KV Cache 与显存

Decode 时每个新 token 都要看到前面所有 token 的 Key/Value。KV Cache 把算过的 K/V 缓存起来避免重算，代价是上下文越长占用显存越多，呈线性关系。

5.3 Prefix Cache

很多请求共享相同开头（固定的长 System Prompt）。Prefix Cache 复用之前算过的 KV，只算新增部分。对 Agent 场景（System Prompt 又长又固定）收益巨大。

5.4 PagedAttention 与连续批处理

vLLM 等框架的核心创新：PagedAttention 像操作系统分页一样按需分配显存；Continuous Batching 让某请求一结束就立刻插入新请求，GPU 不空转，吞吐大幅提升。

5.5 模型路由

按成本/延迟/能力把请求分发到最合适的模型：简单短问题走便宜模型，代码任务走 Claude，复杂长上下文走强力模型。

💼 面试高频题

Prefill 和 Decode 有什么区别？哪个能并行？

Prefill（预填充）：模型一次性读完输入 Prompt，计算所有输入 token 的注意力表示，高度并行，输入越长这步越慢。Decode（解码）：逐个生成输出 token，每生成一个都依赖前面所有 token，天生串行。所以”长输入”主要拖慢 Prefill，”长输出”主要拖慢 Decode。TTFT 基本由 Prefill 决定。

KV Cache 为什么和上下文长度成线性关系？

Decode 时新 token 要和前面每个 token 的 Key/Value 做注意力。为避免重复计算，把每个 token 的 K/V 缓存在显存里。缓存量 ≈ 2(K和V) × 层数 × 隐藏维度 × 序列长度 × batch × 每数字字节数——其中只有序列长度随对话增长，其余是模型固定参数，所以显存占用随上下文长度线性增长。上下文翻 4 倍，KV Cache 显存也翻 4 倍。

Prefix Cache 对 Agent 场景为什么特别有价值？

Agent 的 System Prompt（角色设定 + 大量工具定义）往往又长又固定，且每次请求都带着它。如果每次都重新 Prefill 这段，是巨大浪费。Prefix Cache 识别出”相同的开头”，直接复用之前算好的 KV Cache，只对新增的用户输入做计算——显著降低 TTFT 和成本。多轮对话里前几轮不变的部分同理可复用。

PagedAttention 和 Continuous Batching 分别解决什么？

PagedAttention：传统方式给每个请求预分配一整块连续显存，碎片多、利用率低；PagedAttention 像操作系统虚拟内存分页，按需分配小块，能塞下更多并发请求。Continuous Batching：传统批处理要等一整批都生成完才处理下一批，短请求被长请求拖着空等；连续批处理让任一请求结束就立刻把资源让给排队的新请求，GPU 不空转，吞吐大幅提升。二者是 vLLM 高并发的核心。

TTFT 和吞吐量分别反映什么？如何测？

TTFT（Time To First Token）：从发请求到收到第一个字的时间，决定用户”感觉响应快不快”，主要受 Prefill 和排队影响。吞吐量（tokens/秒）：Decode 阶段整体出字速度，决定”生成一大段要多久”。用流式调用测：记录发起时刻、首 token 到达时刻（算 TTFT）、结束时刻与总字符数（算吞吐）。注意多次采样取中位数，单次受网络抖动影响大。

如何设计一个模型路由策略？

核心是”按请求特征分发到最合适的模型”。基础版用规则：短问题→便宜/免费模型，代码任务→Claude，复杂/长上下文→强力模型，兜底默认模型。进阶版结合：①实时模型排队延迟；②当月成本预算；③模型可用性（出现 403/超时就降级切换）；④用小分类器判断任务难度。目标是在成本、延迟、质量三者间动态平衡。

讲一个你做过的 Agent 项目（STAR 结构）。

Situation：什么业务场景、什么痛点。Task：你要交付的具体目标（如”可恢复的知识问答 Agent，要有引用和审计”）。Action：架构（LangGraph 状态机 + FastAPI 服务 + SqliteSaver 持久化 + RAG 检索 + 危险工具审批），以及关键取舍（为什么用 SSE 不用 WebSocket、为什么按 token 裁剪）。Result：可量化指标——TTFT、成本下降比例、召回准确率、重启恢复能力。重点是讲清楚决策的理由，而不是罗列技术名词。

你的 Agent 如何保证可靠性和安全？

可靠性：持久化 Checkpointer 支撑重启恢复；工具调用做超时/重试/幂等；长任务异步化 + 可取消；全链路 Trace（run_id、耗时、节点轨迹）便于排障。安全：危险工具强制人工审批；长期记忆按 user_id 严格隔离；防 Prompt Injection（最小权限 + 数据/指令分隔 + 参数白名单）；不在日志/Git 里泄露密钥和敏感数据。

如果线上延迟突然变高，你怎么排查？

分层定位：①看 Trace 里各节点耗时，判断是模型调用慢还是某个工具/检索慢；②模型侧看 TTFT 是否升高（可能 Prefill 变长——上下文没裁剪好，或 Prefix Cache 失效）；③看是否排队（并发上来、批处理拥塞）；④检查外部依赖（向量库、数据库、Redis）延迟；⑤必要时触发模型路由降级到更快的模型。核心是先靠指标定位到层，再深入。
